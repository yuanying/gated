# 0008. ingress-nginx からの移行

- Date: 2026-08-21
- Updated: 2026-08-22（並行稼働できないという前提が移行先で成り立たないと分かり、決定をホスト名単位の移行に書き直した）
- Updated: 2026-08-22（1つ移した時点で、ホスト名単位に分解できない集合があると分かり、残りを一括で移す決定に書き直した）
- Status: Accepted

## Context

移行対象のクラスターには Ingress が数えるほどある。その一部が BASIC 認証で保護されており、残りは公開サイトである。証明書はすべて cert-manager が Let's Encrypt から取得している。

なお ingress-nginx がサポートを終える時期が決まっている以上、移行には期限がある。

### 当初の前提と、それが誤っていたこと

この ADR は当初、次の前提に立っていた。

> 新旧2つの Ingress Controller を、外部から同時に到達可能な状態にできない。使えるグローバルアドレスが限られており、80 / 443 は単一の宛先にしか向けられない。

したがって「新コントローラを別の入口で立てて外形を確認し、納得してから切り替える」という段階移行は取れない、という結論だった。

実際の移行先を調べた結果、この前提は成り立たない。3つの事実がある。

1. **ロードバランサのアドレスプールに、グローバルな IPv6 が /96 の単位で入っている。** 新しいコントローラに専用のアドレスを1つ払い出せる。アドレスが限られているのは IPv4 の話であって、v6 側にその制約は無い
2. **境界のルータは、許可した宛先アドレスにだけ 80 / 443 を通す。** 許可の一覧にアドレスを足せば、そのアドレスの 80 / 443 が外から開く。「80 / 443 は単一の宛先にしか向けられない」は単一アドレスへのポート転送を前提にした話で、経路が宛先アドレスごとに独立している環境には当てはまらない
3. **DNS のワイルドカードは、明示のレコードがある名前には適用されない。** ワイルドカードのあるゾーンで、ある名前にレコードを1本作れば、その名前だけが新しい入口に向く。移行の単位がクラスター全体ではなく、ホスト名1つになる

誤りの出どころは、「使えるグローバルアドレスが限られている」を IPv4 の事情として調べたまま、環境全体の性質として一般化したことである。前提を確かめずに、そこから導かれる結論のほうを先に決めていた。

一方、検証用のクラスターが別にあり、そこで実際の Let's Encrypt と実際の Identity Provider に対して動作を確認できることは、当初のとおりである。

### ホスト名単位に分解できない集合があること

1つ移した時点で、上の 3 から導いた「移行の単位がホスト名1つになる」が、対象の全体には及ばないと分かった。

ホスト名を1つだけ移せるのは、その名前に新しい入口を指すレコードを1本作れる場合である。ここで効くのはワイルドカードの性質そのもので、**明示のレコードがある名前にはワイルドカードが一切適用されない。** レコードを1本作った時点で、その名前が持つアドレスは作ったレコードのものだけになり、ワイルドカードが与えていた別のアドレスファミリは消える。

したがってホスト名単位の移行が成り立つのは、新しい入口が**既存の入口と同じアドレスファミリを揃えて**持っている場合に限る。片方のファミリしか持たない入口へ1ホストだけ向ければ、そのホストはもう片方のファミリから到達できなくなる。

新しい入口に専用のアドレスを払い出せるのは、アドレスが潤沢なファミリの側だけである。もう片方のファミリでは境界が転送先を1つしか持てず、新旧に別々のアドレスを与えられない。すでに移したホストは、そのファミリを失った状態で動いている。数が少なく、影響を受ける利用者を把握できていたので受け入れた。

対象の中には、**ワイルドカードが片方のファミリしか与えていないゾーン**がある。そのゾーンのホストは、新しい入口が専用アドレスを持てる側のファミリを、そもそも持っていない。1つ移せばその瞬間に既存のクライアント全部から到達できなくなる。このゾーンはホスト名単位に分解できず、まとめて移すか、移さないかのどちらかしかない。

## Decision

検証用クラスターで確認を完了させたのち、**新旧を並行稼働させ、まず1つ移して確かめ、残りは一括で移す。**

### 段階

1. **検証用クラスターでの確認** — gated をデプロイし、証明書の発行、Identity Provider によるログイン、`NetworkRole` による認可、`AccessToken` による非ブラウザ経路を一通り確認する。外部サービスは本物を使う
2. **新しい入口を立てる** — 本番クラスターに gated を入れ、既存とは別の外部アドレスを払い出し、境界でそのアドレスの 80 / 443 を開ける。既存の Ingress には触れない。gated の IngressClass は既定にしない。既定にすると `ingressClassName` を持たない Ingress が、誰も移すと言っていないのに移る（ADR 0012）
3. **試験用のホスト名で通しを確認する** — 移行対象ではないホスト名を1つ用意し、そこで証明書の発行とログインと認可を本番の環境で確認する。ここまでで既存への影響はまだ無い
4. **1つ移して確かめる** — 影響の小さいホストを1つ選び、Ingress の `ingressClassName` を gated のものへ変更し、BASIC 認証のアノテーションを `NetworkRole` / `NetworkRoleBinding` に置き換え、証明書の発行を依頼するアノテーションを削除する。そのうえで、そのホスト名の DNS レコードを新しい入口へ向ける。**証明書の Secret は新しい名前にし、既存の Secret には触れない**
5. **残りを一括で移す** — 全 Ingress の `ingressClassName` を一度に変え、同じ作業窓の中で、旧コントローラが持っていた外部アドレスを新しい入口へ引き継ぐ。名前ではなくアドレスを移すので、ゾーンのワイルドカードは書き換えずにそのまま新しい入口を指す。段階 4 で足した明示のレコードはこの時点で削除でき、失っていたアドレスファミリが戻る
6. **撤去** — すべて移り、安定を確認したのち、旧コントローラと証明書を発行していたコントローラを削除する

段階 4 を繰り返さないのは、Context に書いたとおり、対象がホスト名単位に分解できないためである。段階 5 では全ホストが同時に止まる。止まるのはアドレスを引き継ぐ数分であり、影響を受ける利用者を把握したうえで受け入れる。

### 旧コントローラ向けのアノテーションは、読み手を失わせるだけにする

移す Ingress には、旧コントローラだけが解釈するアノテーションが付いている。リクエストボディの上限、上流のタイムアウト、BASIC 認証の指定などである。これらは**削除せずそのまま残す。**

gated はアノテーションを一切読まないので（ADR 0012）、残っていても動作は変わらない。残す理由は、どのホストが何を要求していたかを、相当する機能を持つべきかどうかを後で判断する材料として manifest に残すためである。この種の設定は「必要になった時点で、アノテーションではなく独立した表現として足す」と決めてある（ADR 0013）。判断の材料を、移行のついでに消してしまわない。

例外は、残すと害があるものである。クラスを指す非推奨のアノテーションは旧コントローラが拾い続け、`ingressClassName` と食い違う。証明書の発行を依頼するアノテーションは、旧の発行者に新しい名前の Secret へ発行を始めさせ、二重発行になる。この2種は消す。

### 切り戻し

切り戻しはホスト単位で、作ったものを消すだけで済む。Ingress の定義を元に戻し、そのホスト名に足した DNS のレコードを削除すれば、ワイルドカードが効いて元の入口に戻る。

そのために、移したホストの証明書は**新しい名前の Secret** に置く。既存の Secret を上書きすれば、切り戻しは「消す」ではなく「書き戻す」になり、書き戻す先が正しいことを誰も確かめられない。証明書の形式は cert-manager と同じなので（ADR 0005）名前を分けても内容は同じものだが、分けておく理由は互換性ではなく切り戻しの単純さである。

同じ理由で、移行が完了するまで ingress-nginx と cert-manager は残す。

一括で移す段階でも、この性質は保つ。旧コントローラと旧証明書を残したまま切り替え、確認が済んでから撤去する。作業窓の中で駄目だと分かれば、引き継いだアドレスを旧コントローラへ返し、Ingress の定義を戻す。窓を出たあとに1ホストだけ問題が出た場合は、そのホストの `ingressClassName` を旧コントローラへ戻せば、そのホストだけ元に戻る。**これが効くのは旧コントローラがまだ動いている間だけである。だから撤去を急がない。**

### 一括切り替えについての判断が2度変わったこと

当初は一括切り替えを選んだ。「並行稼働の面倒を見る負担」と「事前に検証できない瞬間の回数」を比べ、並行稼働しても後者は減らないと判断したためである。この比較は、並行稼働が取れないという前提の上に立っていた。

前提が誤りだと分かった時点で、比べるものが変わった。「切り替えてみるまで分からない」瞬間は残るが、影響を受けるのはホスト1つで、戻すのはレコード1本である。全サービスに数分の停止を一度に配るより、1サービスずつ配って毎回そこで判断するほうがよい——そう書き直した。

いまは、その判断が及ぶ範囲が限られていると分かっている。ホスト名単位に分解できる集合では前の判断がそのまま正しく、分解できない集合ではそもそも選択肢が無い。分解できない集合を一括で移すなら、分解できる集合を別便で移す理由も薄い。作業窓を2回に分けても、止まる時間の合計は減らないためである。したがって残りは1回で移す。

得たものが無くなったわけではない。段階 4 を1つ通したことで、本物の認証局からの発行と、本物の Identity Provider によるログインと、認可の判定が、本番のクラスターで通ることは確かめてある。一括で移す対象に、まだ一度も動いていない仕組みは含まれていない。

## Consequences

段階 4 までは、既存の Ingress は1つを除いて一切変わらない。そこで止めても、止めた時点の状態が壊れていない。段階 5 にはその性質が無い。始めたら終わらせる作業であり、途中で止めた状態——一部の Ingress だけ新しいクラスを指し、アドレスはまだ旧コントローラにある——は、どのホストも配れていない状態である。作業窓を確保してから始める。

本番固有の問題——外部からの到達性、実トラフィック量、本番のバックエンドが持つ癖（長時間接続、大きなリクエストボディ、WebSocket）——は、最初の1ホストを除いて一度に現れる。「癖の多いバックエンドを最後に回せる」という利点は失われた。代わりに、移す前に確かめる作業がその分だけ増える。旧コントローラのアノテーションが要求していた上限やタイムアウトが、gated では何になるのか——上限が無いのか、何秒で切れるのか——を、移す前に測っておく必要がある。

代償として、移行期間中は2つの Ingress Controller が動く。これは当初の判断が避けたかったものである。期間の長さは移す速度で決まり、放置すれば長くなる。

移したホストから `kubernetes.io/tls-acme` を外すのは、cert-manager と gated が同じホスト名の証明書を同時に取りに行かないためである。Secret 名を分けることと合わせて、発行が二重に走る経路を塞ぐ。それでも同じ名前に対する発行が新旧で交互に起きれば、認証局のレート制限を消費する。移す前の確認は staging のディレクトリで行う。

既存の Ingress は `ingressClassName` の変更だけで移行できる。`spec.tls` をそのまま使い（ADR 0005）、アノテーションの追加は不要である。証明書の Secret 名だけは、上の理由で変える。

BASIC 認証から `NetworkRole` への置き換えは、単なる書き換えではなく認証方式そのものの変更である。保護されている箇所それぞれについて、ブラウザからアクセスされるのか機械からアクセスされるのかを確認し、後者には `AccessToken`（ADR 0004）を用意する必要がある。特に Docker registry のようなものは、クライアント側の資格情報の入れ替えが伴う。一括で移すことにしたため、この確認は移す前に全数について済ませておくことになる。移してから1つずつ確かめる余地は無い。

cert-manager の撤去にあたり、`cert-manager.io/inject-ca-from` を使っている箇所の代替を決める必要がある。gated は CA の注入機能を持たない（ADR 0005）。

これは順序の制約でもある。証明書を発行していたコントローラには、Ingress のための発行以外の利用者がいる。クラスター内部だけで使う証明書を受け取っているコンポーネントや、CA を注入されているコンポーネントである。それらを、自分で証明書を用意する仕組み（多くの chart が同梱している）へ先に切り替えないと、コントローラを消した時点でそのコンポーネントが証明書を失う。撤去の順序は、(1) Ingress 以外の利用者を外す、(2) 全ホストの確認を終える、(3) 旧コントローラと発行元のコントローラを消す、(4) 古い証明書の Secret と旧認証の資格情報を消す、である。(4) を最後に置くのは、それが切り戻しの材料だからである。

この ADR の前提が一度間違っていたことは、他の ADR にも当てはまりうる。環境について述べた前提は、環境を見て確かめるまで前提のままである。

同じ誤りを2度している。1度目は、片方のアドレスファミリについて調べたことを環境全体の性質として一般化した。2度目は、確かめた1つのゾーンの性質を全ゾーンに一般化して「移行の単位がホスト名1つになる」と書いた。どちらも、確かめた範囲を書かずに結論だけを書いたために起きている。
