# 0008. ingress-nginx からの移行

- Date: 2026-08-21
- Updated: 2026-08-22（並行稼働できないという前提が移行先で成り立たないと分かり、決定をホスト名単位の移行に書き直した）
- Status: Accepted

## Context

移行対象のクラスターには Ingress が数えるほどある。その一部が BASIC 認証で保護されており、残りは公開サイトである。証明書はすべて cert-manager が Let's Encrypt から取得している。

なお ingress-nginx がサポートを終える時期が決まっている以上、移行には期限がある。

### 当初の前提と、それが誤っていたこと

この ADR は当初、次の前提に立っていた。

> 新旧2つの Ingress Controller を、外部から同時に到達可能な状態にできない。使えるグローバルアドレスが限られており、80 / 443 は単一の宛先にしか向けられない。

したがって「新コントローラを別の入口で立てて外形を確認し、納得してから切り替える」という段階移行は取れない、という結論だった。

実際の移行先を調べた結果、この前提は成り立たない。3つの事実がある。

1. **ロードバランサのアドレスプールに、グローバルな IPv6 が /96 の単位で入っている。** 新しいコントローラに専用のアドレスを1つ払い出せる。アドレスが限られているのは IPv4 の話であって、v6 側にその制約は無い
2. **境界のルータは、許可した宛先アドレスにだけ 80 / 443 を通す。** 許可の一覧にアドレスを足せば、そのアドレスの 80 / 443 が外から開く。「80 / 443 は単一の宛先にしか向けられない」は単一アドレスへのポート転送を前提にした話で、経路が宛先アドレスごとに独立している環境には当てはまらない
3. **DNS のワイルドカードは、明示のレコードがある名前には適用されない。** ワイルドカードのあるゾーンで、ある名前にレコードを1本作れば、その名前だけが新しい入口に向く。移行の単位がクラスター全体ではなく、ホスト名1つになる

誤りの出どころは、「使えるグローバルアドレスが限られている」を IPv4 の事情として調べたまま、環境全体の性質として一般化したことである。前提を確かめずに、そこから導かれる結論のほうを先に決めていた。

一方、検証用のクラスターが別にあり、そこで実際の Let's Encrypt と実際の Identity Provider に対して動作を確認できることは、当初のとおりである。

## Decision

検証用クラスターで確認を完了させたのち、**新旧を並行稼働させ、ホスト名を1つずつ移す。**

### 段階

1. **検証用クラスターでの確認** — gated をデプロイし、証明書の発行、Identity Provider によるログイン、`NetworkRole` による認可、`AccessToken` による非ブラウザ経路を一通り確認する。外部サービスは本物を使う
2. **新しい入口を立てる** — 本番クラスターに gated を入れ、既存とは別の外部アドレスを払い出し、境界でそのアドレスの 80 / 443 を開ける。既存の Ingress には触れない。gated の IngressClass は既定にしない。既定にすると `ingressClassName` を持たない Ingress が、誰も移すと言っていないのに移る（ADR 0012）
3. **試験用のホスト名で通しを確認する** — 移行対象ではないホスト名を1つ用意し、そこで証明書の発行とログインと認可を本番の環境で確認する。ここまでで既存への影響はまだ無い
4. **1つずつ移す** — ホストごとに、Ingress の `ingressClassName` を gated のものへ変更し、BASIC 認証のアノテーションを `NetworkRole` / `NetworkRoleBinding` に置き換え、`kubernetes.io/tls-acme` アノテーションを削除する。そのうえで、そのホスト名の DNS レコードを新しいアドレスへ向ける。**証明書の Secret は新しい名前にし、既存の Secret には触れない**
5. **撤去** — すべて移り、安定を確認したのち ingress-nginx と cert-manager を削除する

段階 4 は繰り返しである。影響の小さいホストから始め、1つ移すごとに次へ進むかを判断する。

### 切り戻し

切り戻しはホスト単位で、作ったものを消すだけで済む。Ingress の定義を元に戻し、そのホスト名に足した DNS のレコードを削除すれば、ワイルドカードが効いて元の入口に戻る。

そのために、移したホストの証明書は**新しい名前の Secret** に置く。既存の Secret を上書きすれば、切り戻しは「消す」ではなく「書き戻す」になり、書き戻す先が正しいことを誰も確かめられない。証明書の形式は cert-manager と同じなので（ADR 0005）名前を分けても内容は同じものだが、分けておく理由は互換性ではなく切り戻しの単純さである。

同じ理由で、移行が完了するまで ingress-nginx と cert-manager は残す。

### 一括切り替えを採らない理由（当初の判断の扱い）

当初は一括切り替えを選んだ。「並行稼働の面倒を見る負担」と「事前に検証できない瞬間の回数」を比べ、並行稼働しても後者は減らないと判断したためである。

この比較は、並行稼働が取れないという前提の上に立っていた。並行稼働が取れるなら、比べるものが変わる。「切り替えてみるまで分からない」瞬間は依然として残るが、その瞬間に影響を受けるのはホスト1つであり、戻すのはレコード1本である。全サービスに数分の停止を一度に配るのと、1サービスずつ配って毎回そこで判断できるのとでは、後者を選ばない理由が無い。

## Consequences

既存の Ingress は、その番が来るまで一切変わらない。移行の途中で止めても、止めた時点の状態が壊れていない。

本番固有の問題——外部からの到達性、実トラフィック量、本番のバックエンドが持つ癖（長時間接続、大きなリクエストボディ、WebSocket）——は、一度にではなく1ホストずつ現れる。最初に移すものを選べるので、癖の多いバックエンドを最後に回せる。逆に、癖は移してみるまで分からないままである。

代償として、移行期間中は2つの Ingress Controller が動く。これは当初の判断が避けたかったものである。期間の長さは移す速度で決まり、放置すれば長くなる。

移したホストから `kubernetes.io/tls-acme` を外すのは、cert-manager と gated が同じホスト名の証明書を同時に取りに行かないためである。Secret 名を分けることと合わせて、発行が二重に走る経路を塞ぐ。それでも同じ名前に対する発行が新旧で交互に起きれば、認証局のレート制限を消費する。移す前の確認は staging のディレクトリで行う。

既存の Ingress は `ingressClassName` の変更だけで移行できる。`spec.tls` をそのまま使い（ADR 0005）、アノテーションの追加は不要である。証明書の Secret 名だけは、上の理由で変える。

BASIC 認証から `NetworkRole` への置き換えは、単なる書き換えではなく認証方式そのものの変更である。保護されている箇所それぞれについて、ブラウザからアクセスされるのか機械からアクセスされるのかを確認し、後者には `AccessToken`（ADR 0004）を用意する必要がある。特に Docker registry のようなものは、クライアント側の資格情報の入れ替えが伴う。ホスト単位で移せるので、この確認もホスト単位で行える。

cert-manager の撤去にあたり、`cert-manager.io/inject-ca-from` を使っている箇所の代替を決める必要がある。gated は CA の注入機能を持たない（ADR 0005）。

この ADR の前提が一度間違っていたことは、他の ADR にも当てはまりうる。環境について述べた前提は、環境を見て確かめるまで前提のままである。
