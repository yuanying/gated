# 0019. 認可の責務をレプリカ間でどう分けるか

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0006 は責務をレプリカごとに分け、認可の判定を全レプリカの仕事とした。ADR 0016 は、その分け方を登録経路の性質として機械的に検査すると決めた。データプレーンを組み立てる経路が登録した runnable はリース不要、証明書を組み立てる経路が登録した runnable はリース必須である。

認可を実装すると、この2つのどちらとも言い切れない runnable が出てくる。権限のスナップショットを作り直す reconciler は全レプリカに要る。一方 `targetRef` の解決結果を status に書き戻す reconciler は、全レプリカが動くと全員が同じ内容を書く。

## Decision

### スナップショットはデータプレーン、status はリーダー

権限のスナップショットを組み立てる reconciler は、データプレーンの登録経路に置き、リースを要求しない。判定できないレプリカは 404 を返すのではなく、求められたものを返してしまう（ADR 0017）。ルーティングテーブルを持たないレプリカより悪い。

`NetworkRole` と `NetworkRoleBinding` の status を書き戻す reconciler は、リーダー限定にする。全レプリカが書けば、同じ内容の書き込みと同じ内容のイベントがレプリカ数だけ増える。とくにイベントは、fail-open の穴を人に見せるためのものなので、同じ警告が3つ並ぶと読む側の役に立たない。書き込みが増えても誰も新しいことを知らない。

status の書き戻しが止まっている間に何が起きるかも、リーダー限定でよい理由になる。止まるのは表示であって判定ではない。リーダーが居ない間も全レプリカは判定を続ける。これは、リーダーが居ない間に止まるのが証明書の取得だけである（ADR 0006）のと同じ性質である。

### 検査は経路の一覧として書く

ADR 0016 の検査は、データプレーンの経路1つとリーダー限定の経路1つを名指ししていた。リーダー限定の経路が2つになったので、検査を「経路の集合」として書き直し、それぞれの集合に対して同じ性質を確かめる形にする。

こうしておくと、あとの段階が reconciler を足すときにすることは、どちらかの集合に登録関数を1つ加えることだけになる。検査そのものは書き換えなくてよい。書き換えが要るのは ADR 0006 の表を変えるときだけ、という ADR 0016 の性質は保たれる。

リーダー限定であるべき runnable も、controller-runtime の既定に乗るのではなく、リースが要ることを自分で宣言する。既定がどちらであっても意味の変わらない書き方にする、という ADR 0016 の方針をそのまま適用する。

## Consequences

リーダーを取れなかったレプリカも、権限を読み、判定し、拒否できる。2レプリカの envtest はこれをフォロワー側で確かめる。ルーティングと証明書について ADR 0016 が置いた assertion の隣に、認可の行が1つ増えた形になる。

status の書き戻しがリーダーの仕事になったので、リーダーが居ない間に `NetworkRole` を適用すると、しばらく status が空のままになる。適用した人からは「まだ何も書かれていない」と見える。判定のほうは既に効いているので、見えている状態と実際の状態がずれる時間がある。リースの満了までなので短い。
