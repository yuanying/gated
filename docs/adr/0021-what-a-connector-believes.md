# 0021. コネクタが何を信じ、何を設定で受け取るか

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0003 は GitHub と Google のコネクタを自前で実装すると決め、Google の ID トークンについて `email_verified` を必ず確認せよと名指しで警告した。書かれていないのは、その確認をどう「必ず」にするか、ID トークンの検証で他に何を固定するか、そしてプロバイダの実際のエンドポイントをどこから受け取るかである。

確認の抜けは、抜けたことが観測できない種類の失敗である。未検証のアドレスを信じたコードパスは、正常に動いているように見える。テストで列挙するだけでは、あとから足された2本目の経路を守れない。

ID トークンの検証にも同じ性質がある。JWT はアルゴリズム名を**トークン自身が名乗る**。名乗りに従う実装は `none` を渡され、あるいは誰でも読める公開鍵の係数を鍵とした HMAC を渡される。どちらも「検証に成功した」という形で失敗する。

## Decision

### 検証済みであることを型にする

ID トークンの claim から Google の主体を作れる関数は1つだけとし、その引数の型は「検証済みのアドレス」を表す非公開の型にする。その型の値を作れる関数もまた1つだけで、そこが `email_verified` を見る。

こうすると、確認を飛ばして主体を作る経路はコンパイルが通らない。テストは2種類置く。プロバイダの答え（真・偽・欠落・文字列の "true"・数値）を列挙する表と、パッケージ自身のソースを読んで「主体の接頭辞が書かれているのはその1関数だけである」ことを確かめるものである。後者は、型を迂回して文字列を組み立てる経路が足されたときに落ちる。

`email_verified` は真偽値として読む。文字列の `"true"` を返すプロバイダがあっても、そこで解釈を広げると「検証済みでないものを検証済みと読む」方向に倒れる。読めなければ拒否する。

### ID トークンの署名アルゴリズムは固定する

受け付けるのは RS256 だけとし、トークンが名乗る他のアルゴリズムはすべて拒否する。`iss`・`aud`・`exp` も確認する。`iat` には2分の許容を置くが、`exp` には置かない。ID トークンは発行から数秒で検証するので、プロバイダが期限切れと言ったものを延命する理由がない。

鍵は JWKS から取り、`kid` で引く。知らない `kid` が来たら鍵集合を取り直すが、取り直しには最短間隔を設ける。存在しない `kid` を並べたトークンを送り続けられると、プロバイダへの要求が同じ数だけ出ることになる。

`iss` の比較だけは緩める。discovery が URL で名乗り、トークンには scheme 抜きのホスト名を書くプロバイダが実在する（Google 自身がそうしていた）ため、その2形だけを同一視する。それ以外は一致を要求する。

ID トークンには nonce を要求する。中央認証ホストが state 用に作った乱数のダイジェストを nonce として渡し、戻ってきた ID トークンがそれを持っていることを確かめる（ADR 0020）。別のログインで得た ID トークンをこのログインに差し込めなくなる。

### プロバイダのエンドポイントは設定で受け取る

GitHub の OAuth エンドポイントと REST API のルート、Google の OIDC issuer を、それぞれ起動フラグにする。既定は github.com / api.github.com / accounts.google.com とする。

これらは ADR 0009 の分類でいう「どこで動かしても同じでよい値」なので既定を持たせてよい。フラグにするのは2つの理由からである。GitHub Enterprise を使う構成が別のホストを持つこと、そして ADR 0007 が求める「モック IdP に対する E2E」が、これを差し替えられなければ成立しないことである。

コード内に本物のエンドポイントが定数として残るが、これはプロバイダが公開している固定値であって、運用している環境について何も述べていない。

### コネクタの client secret は読み取り元を interface で受け取る

client secret は Secret に置かれ、プロセスの起動時にまだ存在しないことも、あとで差し替えられることもある。コネクタはそれを「文字列」ではなく「文字列を返すもの」として受け取り、交換のたびに読む。読めなければ、空の secret で交換に行かずにその場で失敗する。空で行くと、プロバイダからはクライアントの設定ミスとして返ってきて、Secret がまだ届いていないだけだという事実が見えなくなる。

session の署名鍵と違い、client secret は gated が生成できない。プロバイダが発行するものなので、手で置く。

## Consequences

`email_verified` の確認は、思い出す対象ではなく型の制約になった。ADR 0003 が名指しで警告した失敗は、コンパイラとテストの2重で塞がれている。

アルゴリズムを固定したので、プロバイダが将来 ES256 などへ移行した場合は gated 側の変更が要る。名乗りに従う実装にしておけば追従は不要だが、それは受け取ってはならないものまで受け取る実装である。追従の手間を選ぶ。

エンドポイントをフラグにしたことで、E2E がモックの Identity Provider に対して通しで動かせるようになった。同時に、フラグを誤って向ければ gated は偽のプロバイダを信じる。これは ACME のディレクトリ URL と同じ性質の設定であり、同じ扱い——起動時に形を検証し、値そのものは運用者の責任——とする。

コネクタを自前で持つ以上、プロバイダ側の仕様変更に追従する責任は ADR 0003 が既に引き受けている。ここで固定した項目は、その追従が必要になる箇所の一覧でもある。
