# 0007. テスト戦略

- Date: 2026-08-21
- Status: Accepted

## Context

gated はクラスターのすべての HTTP トラフィックの入口になる。壊れれば全サービスが同時に落ちる。加えて認可の誤りは、落ちるのではなく「本来見えないものが見える」という静かな失敗として現れる。

一方でこれは個人で運用するプロジェクトであり、テストの整備に無限の時間をかけられるわけではない。壊れると困る部分に労力を集中させる必要がある。

扱う要素は性質が大きく異なる。認可の判定は入力から出力が一意に決まる純粋な計算である。CRD の Reconcile は Kubernetes API サーバとの相互作用である。ACME と OIDC は外部サービスとの通信を伴う。それぞれに適した検証の方法が違う。

## Decision

層ごとに異なる道具を使う。

| 層 | 道具 | 対象 |
|---|---|---|
| 純関数ユニットテスト | 標準の testing、テーブルテスト | 認可判定、ルーティングのマッチング、証明書の更新要否判定 |
| 結合テスト | envtest（本物の apiserver + etcd）、フェイクサーバ | CRD の Reconcile、ACME クライアント、OIDC コネクタ |
| E2E | kind + Pebble + モック IdP | シナリオを絞った通し確認 |

### 純関数として切り出すもの

認可の判定を、Kubernetes の型に依存しない純粋な関数として実装する。入力は「主体・リクエストの属性（ホスト、パス、メソッド）・権限の集合」であり、出力は「許可・拒否・要ログイン」である。informer のキャッシュも HTTP のリクエストオブジェクトも受け取らない。

閲覧可否の判定を単一の関数に集約する形である。こうすることで、`system:unauthenticated` に GET だけを許した状態で POST が来た場合、複数の `NetworkRole` が重なった場合、`targetRef` が解決できなかった場合といった分岐を、クラスターを立ち上げずにすべて列挙して確かめられる。

ルーティングのマッチング（ホストとパスから宛先を決める規則）と、証明書の更新要否の判定（有効期限と現在時刻から更新すべきかを決める規則）も同様に純関数として切り出す。

### envtest を使う範囲

CRD の Reconcile は envtest で検証する。本物の API サーバと etcd を起動するため、CRD のスキーマ検証、`status` の書き戻し、informer の伝播といった、モックでは再現できない挙動を確かめられる。fake client では CRD のバリデーションが効かないため、スキーマの誤りを取り逃す。

ACME クライアントは Pebble（Let's Encrypt が提供する ACME テストサーバ）に対して動かす。OIDC コネクタは、認可コードとトークンを返すフェイクの Identity Provider に対して動かす。いずれも本物の外部サービスには接続しない。

### E2E の範囲

kind クラスターに gated をデプロイし、Pebble とモック IdP を同居させ、通しのシナリオを確認する。シナリオは絞る。

- Ingress を適用すると証明書が発行され、HTTPS で応答が返る
- `NetworkRole` を適用すると未ログインのアクセスがログインへ誘導される
- ログイン後、許可された主体はアクセスでき、許可されない主体は 403 になる
- `AccessToken` で `Authorization: Bearer` と BASIC 認証のパスワード欄の双方が通る

E2E を網羅に使わない。網羅は純関数ユニットテストの仕事である。

### 進め方

原則としてテスト駆動開発で進める。期待される入出力に基づきテストを先に書き、失敗を確認してから実装する。実装中はテストを変更せず、実装を修正する。

## Consequences

認可の分岐を網羅的に、かつ高速に検証できる。認可の誤りは静かな失敗として現れるため、ここに網羅性を置くことが最も費用対効果が高い。

envtest により CRD のスキーマと Reconcile の挙動が実際の API サーバに対して検証される。CRD の定義ミスを本番のクラスターで発見する事態を避けられる。

E2E を絞ったため、層の境界をまたぐ結合の誤りを取り逃す可能性が残る。特に「純関数は正しいが、そこへ渡す入力の組み立てが間違っている」という失敗は、ユニットテストでも envtest でも見つからない。E2E のシナリオはこの境界を通ることを意識して選ぶ必要がある。

envtest と kind の実行にはバイナリのダウンロードと相応の実行時間が必要になる。日常の開発ループでは純関数ユニットテストだけを回し、envtest 以上は明示的に実行する構成にする。

外部サービスに接続しないため、テストはネットワークの状態に左右されず、Let's Encrypt のレート制限も消費しない。代償として、本物の Let's Encrypt と本物の Identity Provider に対する検証は、test クラスターでの手動確認（ADR 0008）に委ねられる。
