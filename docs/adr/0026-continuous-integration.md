# 0026. CI は Makefile のターゲットだけを呼び、live 層は仕組みで締め出す

- Date: 2026-08-21
- Status: Accepted

## Context

テストは揃っている。純関数ユニット、envtest、Pebble に対する結合、kind での E2E、そして lint（ADR 0007 / 0011 / 0024）。しかし誰かが手元で走らせない限り、どれも実行されない。初期実装の PR は checks が一つも無いままマージされた。

同時に、この構成には「絶対に自動で走らせてはいけない層」が一つある。ADR 0025 の live 層である。実在の認証局に注文を出し、実在の DNS ゾーンのレコードを書き換える。レート制限は週単位でしか回復せず、ゾーンを操作できる API トークンを要する。

「CI の設定に書かなければ走らない」のは事実だが、それは今の設定の話でしかない。ワークフローを足すのも書き換えるのも、この先ずっと簡単である。事故が起きるとしたら、E2E のジョブをコピーして tag を差し替えたとき、あるいは「全部のテストを走らせる」ジョブを親切心で足したときである。どちらも悪意を要しない。

## Decision

### CI は既存の Makefile ターゲットを呼ぶだけにする

ADR 0011 はテストの入口を Makefile に置くと決めた。CI はその利用者の一人であり、独自の入口を持たない。ジョブがすることは、チェックアウトして Go を用意して `make` のターゲットを一つ呼ぶことだけである。

こうすると、CI が赤いときに手元で再現する手順が「同じターゲットを呼ぶ」で済む。CI でしか走らないコマンドがあると、CI でしか出ない失敗が生まれる。

### 層ごとにジョブを分ける

| ジョブ | 呼ぶもの | 何を見るか |
|---|---|---|
| no-live-layer | （後述の検査） | live 層が CI に入り込んでいないこと |
| vet | `make vet` | go vet と gofmt |
| lint | `make lint` | golangci-lint（タグ別に3パス） |
| unit | `make test` | 純関数ユニットテスト |
| generate | `make generate` と作業ツリーの差分 | 生成物が最新であること（ADR 0011） |
| envtest | `make test-envtest` | 本物の apiserver に対する CRD と Reconcile |
| integration | `make test-integration` | Pebble とフェイク IdP |
| e2e | `make test-e2e` | kind クラスターでの通し |

速い層を遅い層の後ろに並べない。gofmt の掛け忘れを知るのに E2E の完了を待つ理由が無い。ジョブの間に依存関係を置かないので、8 つが同時に走り、速いものから順に結果が返る。

### live 層を締め出すのは、書かないことではなく落ちること

`no-live-layer` ジョブが `.github/workflows/` 配下を全文検索し、次のいずれかが見つかったら失敗する。

1. live 層の Makefile ターゲット、または `live` タグを付けた `go test` の実行
2. 秘密情報の参照、および live 層が読む環境変数の名前

1 が直接の締め出しである。2 は二重目で、ADR 0025 が「環境に属する値に既定値を持たせず、未設定なら理由を述べて skip する」と決めているため、仮に 1 をすり抜けても、渡すものが無ければ live 層は何にも到達せず skip する。この二つは互いに独立に効く。

三重目として、ワークフローの権限は既定で読み取りのみとし、どのジョブもそれを広げない。

検査は追加の依存を持たず、他のどのジョブよりも先に終わる。違反したワークフローは、重いジョブが動き出す前に赤くなる。

lint は live タグの付いたファイルをコンパイルするので（ADR 0025 がハーネスを共有しているため）、タグの名前が出てくること自体は正常である。検査が見るのは「テストの実行」であって、タグへの言及ではない。

副作用として、ワークフローのコメントに live 層のターゲット名を書けなくなる。検査は自分自身も含めて全文を見るからである。この不便さは、検査に例外を持たせないことと引き換えである。

### 秘密情報を一つも使わない

CI は秘密情報を要求しない。fork からの PR でも全ジョブがそのまま走る。上の検査 2 は、この性質が壊れたことにも気づく。

### バージョンは一箇所からしか取らない

Go のバージョンはワークフローに書かず、`go.mod` から読む。数字を二箇所に書けば、いつか片方だけが更新される。

外部の action は commit SHA で固定し、対応するタグを注記する。タグは可動であり、後から別のコミットを指せる。SHA は実際に走ったものと一致する。固定した SHA を人が追うことはできないので、更新は依存の自動更新に任せる。

### キャッシュは「壊れても嘘をつかない」ものに限る

Go のモジュールとビルドのキャッシュだけを使う。キーは `go.sum` である。モジュールのキャッシュは `go.sum` のハッシュで検証されるため、内容が壊れていればダウンロードし直しになり、テストが通ってしまうことはない。ビルドキャッシュも同様で、外れれば再コンパイルになるだけである。

テストの結果そのものや、「変更が無ければ層ごと skip する」類の仕組みはキャッシュしない。キャッシュの誤りがそのまま緑になるものは、CI が答えるべき問いに嘘で答える。

envtest のコントロールプレーンのバイナリと kind のイメージもキャッシュしない。取得は層の実行時間に対して短く、古い写しを掴むと「誰も指定していないバージョンに対して検証していた」という分かりにくい状態になる。

### 同じ PR の古い実行は打ち切る

PR に push が続いたら、その PR の実行中のものを打ち切る。main への push は打ち切らない。main の各コミットにはそれぞれの結果が要る。

すべてのジョブに timeout を置く。層ごとの所要時間に対して余裕を持たせた値で、無限に回り続けるものを止めるための上限である。

## Consequences

PR ごとに全層が回る。手元で `make test` しか走らせていない変更でも、envtest と E2E の結果が付く。

live 層が CI に紛れ込む経路が、単なる不作為ではなく検査に変わった。ワークフローを書き換える人は、締め出しの存在を知らなくても、赤くなったときに理由を読む。

E2E のジョブは数分かかり、runner の docker に依存する。runner の docker やネットワークの都合で落ちたとき、gated の欠陥と区別が付きにくい。層を分けてあるので、どのジョブが落ちたかは分かる。

action を SHA で固定したため、更新は自動化が入るまで滞る。タグ追従に比べて、脆弱性修正が入る時期が遅れうる。

生成物の検査は、生成物をコミットする方針（ADR 0011）が守られているかを見るだけで、生成の内容が正しいかは見ない。内容は envtest がコミット済みの YAML を読むことで検証される。
