# 0017. 認可の評価と、まだ何も知らない状態

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0002 は認可のモデルを決めた。`NetworkRole` が保護対象と許す操作を宣言し、`NetworkRoleBinding` がそれを主体に結び付ける。どの `NetworkRole` からも参照されない Ingress は素通しで、複数の宣言が重なれば許可の和になり、拒否の規則は持たない。ADR 0007 はその判定を純関数として切り出すことも決めた。

決まっていないのは、その2つのリソースからどうやって「権限の集合」を組み立てるか、そして組み立てられていない間に届いたリクエストをどう扱うかである。

後者が問題になるのは、素通しの既定と、起動直後の無知が、値として同じ形をしているからである。「どの `NetworkRole` からも参照されていない」も「まだ何も読んでいない」も、権限の集合が空であることに変わりはない。純関数はこの2つを区別できない。区別する材料を持っていないからである。

## Decision

### 保護は Role から、許可は Binding から来る

対象が保護されているかどうかは、`NetworkRole` がその対象を参照しているかだけで決まる。許可は `NetworkRoleBinding` が与えた主体の分だけ生まれる。

したがって、束ねられていない `NetworkRole` は「保護されているが誰も通れない」を意味する。規則を持たない `NetworkRole` も同じである。どちらも RBAC の読み方をそのまま持ってきたもので、権限を書く操作と権限を与える操作を独立させた ADR 0002 の分離が、そのまま判定の形になっている。

`Binding` が届くのは同じ namespace の `NetworkRole` だけである。namespace を越えて届くなら、binding を書ける者が、自分の持ち物でない namespace の何かを開けられることになる。

### 解決できなかった参照は、権限の集合に現れない

`targetRef` が解決できなかった `NetworkRole` は、保護対象を持たないものとして扱う。その結果、保護したかった Ingress は誰からも参照されていないことになり、素通しになる。

これは ADR 0002 が受け入れた fail-open の帰結そのものである。ここで代わりに拒否を選ぶこともできるが、そうすると「名前を打ち間違えると、そのリソースだけでなく、たまたま同じ名前を指していた他の宣言まで巻き添えで閉じる」という別の壊れ方を作る。fail-open を選んだ以上、穴は穴として開けたうえで、開いていることを外から見えるようにする（後述）。

### パスの前方一致は、ルーティングのそれと意味が違う

パスの語彙は RBAC の `nonResourceURLs` に合わせる（ADR 0010）。末尾の `*` による前方一致は、RBAC と同じく**文字列としての前方一致**であって、パスセグメントの境界は見ない。ルーティングの `Prefix` は境界を見る（ADR 0012）。同じ語で呼ばれる2つの規則が違う意味を持つことになる。

揃えなかったのは、2つが答えている問いが違うからである。ルーティングで広く一致することは、宣言していない側のトラフィックを奪うことであり、奪われた側からは見えない。認可で広く一致することは、書いた本人が意図より多く許すことである。前者は他人に起きるが、後者は書いた本人に起きる。借りてきた語彙の意味を勝手に狭めるより、借りたまま使い、途中にワイルドカードを含むパスをスキーマで拒否する（ADR 0010）ほうが、書いたものと読まれるものが一致する。

メソッドは大文字小文字を区別して比較する。HTTP のメソッド名は元から区別されるものであり、ここで畳むと、書かれていない許可が少しだけ増える。増える方向の誤りは報告されない。

リクエストのパスもメソッドも、届いた形のまま比較する。ルーティングも正規化しない（ADR 0012）ので、認可を通ったパスと転送されるパスは同じ文字列である。

### 何も読んでいない間はリクエストを断る

権限のスナップショットが一度も届いていないレプリカは、届いたリクエストに 503 を返す。あわせて、スナップショットの到着を readiness の条件にする。

素通しの既定を持つ以上、「まだ読んでいない」を「保護されていない」として扱うと、起動直後の一瞬だけ全部が開く。その一瞬は普段は誰にも当たらないが、当たったときには何も記録が残らない。ルーティングテーブルは同じ状況で 404 を返すので、そちらは安全側に倒れており、追加の細工が要らない。

### 解決できなかった参照は status とイベントの両方に出す

`NetworkRole` の `status.resolvedTargets` に解決できた対象とそのホスト名を書き、`TargetResolved` condition に可否を書く。解決できなければ警告イベントも記録する。`NetworkRoleBinding` の `RoleResolved` も同じ扱いにする。

両方に出すのは、片方だけでは見つからないからである。condition は残るが、見にいかなければ出てこない。イベントは namespace を眺めていれば目に入るが、しばらくすると消える。文面には「見つからなかった」ではなく「その Ingress は認証なしで公開されている」と、起きている結果のほうを書く。

解決できたかどうかは、その Ingress が存在するかだけで決める。ingress class は見ない。gated が扱わない class の Ingress は gated を通らないので、そこに穴は開かない。

## Consequences

判定は対象ごとの許可の和になり、評価順序に依存しない。どのレプリカでも、informer が何を先に返したかに関わらず、同じ入力から同じ答えが出る。

`NetworkRole` を書いて `NetworkRoleBinding` を忘れると、対象は全員に対して閉じる。開きっぱなしになるより気付きやすい失敗であり、ログインしても通れないので「要ログイン」ではなく拒否として現れる。

起動直後の短い間、そのレプリカは 503 を返す。readiness を条件にしたので、通常はロードバランサがそのレプリカへ送り始める前に終わっている。ここで可用性をわずかに削っているが、削らない側の選択肢は「一瞬だけ全部を公開する」である。

パスの前方一致が2箇所で違う意味を持つことは、読む人を一度は驚かせる。ルーティングの規則と認可の規則を同じ気持ちで読めない。
