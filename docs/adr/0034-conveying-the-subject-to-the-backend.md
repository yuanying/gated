# 0034. バックエンドに主体を署名付きで伝える

- Date: 2026-10-15
- Updated: 2026-10-16（無ければ鍵をリーダーが生成する、を ADR 0035 で置き換えた。古い版がリーダーのまま残ると誰も鍵を作らず、版上げが止まったため）
- Status: Accepted

## Context

gated は誰がログインしたかを確かめるが、それをバックエンドへ伝えない。確定した主体はプロセスの中で認可の判定に使われるだけで、転送するリクエストには載らない（ADR 0018）。転送のときに足すのは `X-Forwarded-*` と `X-Real-IP` だけで、落とすのは gated 自身の Cookie と照合できた `AccessToken` だけである（ADR 0013、ADR 0022）。

このため、バックエンドは「この要求が gated を通り、誰の要求なのか」を自分で確かめられない。gated が守っている限りは、守られた Ingress には許された主体の要求しか届かないので、それで足りるように見える。しかし gated を通らずにバックエンドへ届く道が2つある。

1つは、クラスターの中から Service へ直接届く道である。NetworkPolicy が効いていないクラスターでは、どの Pod からでもバックエンドの Service を叩ける。gated の認可はそこでは何もしない。

もう1つは、gated の設定が fail-open になったときである。`NetworkRole` の `targetRef` を書き間違えれば、守ったつもりの Ingress は誰からも参照されず、素通しになる（ADR 0002、ADR 0017）。Ingress をパスで分けていれば、守る側の Ingress を消しただけで、そのパスは守られていない Ingress に吸われる（ADR 0012）。どちらも静かに起き、気付くまでインターネットから認証なしで届く。

バックエンドがこの2つを自分で断るには、gated が「この主体の要求を、このホストへ通した」ことを、バックエンドが検証できる形で渡す必要がある。主体を素のヘッダで渡すだけでは足りない。クラスターの中の誰でも、同じヘッダを付けて直接 Service を叩ける。gated の後ろに置かれた要求のヘッダは、クライアントが付けたものも今はそのまま届くので（ADR 0013 が捨てるのは転送ヘッダだけである）、外からでも名乗れる。

## Decision

### 主体が決まった要求には、署名した主張を1つ付ける

gated は、バックエンドへ転送する要求のうち、主体が決まっているものに、署名した短い主張（以下「アサーション」）をヘッダ1つで付ける。主体が決まっていない要求——未ログインで `system:unauthenticated` に許された要求、どの `NetworkRole` にも参照されない Ingress への未ログインの要求——には何も付けない。

アサーションが言うのは「gated はこの主体を、このホストへの要求について認証した」ことであり、「この要求を許可した」ことではない。転送されている時点で認可は通っているが、どの規則で通ったかは載せない。バックエンドは載っている主体を見て、自分が許す相手かどうかを自分で決める。

認可の結果ではなく認証の結果を伝えるのは、fail-open のときにも正しい意味を保つためである。素通しになった Ingress に未ログインで来た相手にはアサーションが付かないので、バックエンドはそれを断れる。ログイン済みの相手には付くが、その主体は本当にその人であり、許すかどうかはバックエンドの設定が決める。認可の結果を名乗らせると、素通しが「許可」として伝わってしまう。

主体の入口は問わない。セッション Cookie で決まった主体も、`AccessToken` で決まった主体も、同じアサーションになる。入口は2つで仕組みは1つ、という ADR 0004 の形をここでも崩さない。`AccessToken` は長命だが、アサーション自体は下に書く短い期限を持つので、バックエンドに届くのは長命の資格情報ではない。

付けるかどうかを Ingress ごとに切り替える手段は持たない。gated は Ingress のアノテーションを読まない（ADR 0001、ADR 0012）。アサーションを読まないバックエンドにとっては、知らないヘッダが1つ増えるだけで、挙動は変わらない。将来、特定の対象にだけ付けたい理由が出てきたら、そのときは `NetworkRole` の側に表現を足す。

### 形は JWS の compact 形式、署名は Ed25519

アサーションは JWS の compact 形式（いわゆる JWT）とし、署名のアルゴリズムは EdDSA（Ed25519）に固定する。

| 部分 | 項目 | 中身 |
|---|---|---|
| ヘッダ | `alg` | `EdDSA` だけ |
| ヘッダ | `typ` | `gated-assertion+jwt`。他の用途の JWT と取り違えないための明示的な型 |
| ヘッダ | `kid` | 署名した鍵の識別子。公開鍵の JWK thumbprint |
| 本体 | `iss` | 中央認証ホストの https の origin。どの gated が発行したかを示す |
| 本体 | `sub` | 主体。ADR 0002 の語彙そのまま（`github:<login名>` など） |
| 本体 | `aud` | 要求のホスト名。小文字にし、ポートを含まない。ワイルドカードの規則に当たった場合も、規則ではなく要求の名前 |
| 本体 | `iat` | 発行時刻 |
| 本体 | `exp` | 期限。発行から60秒 |

セッションや handoff で使っている gated 独自の署名形式（ADR 0003、ADR 0020）を流用しなかったのは、読み手が違うからである。あちらは gated 自身しか読まないので、形を自由に決められた。アサーションはバックエンドが読む。バックエンドは言語も作り手も様々で、独自形式にすると、それぞれが検証の実装を一から書くことになる。JWS なら、主要な言語に検証のライブラリが既にあり、公開鍵の配り方（JWKS）まで含めて決まった形がある。

アルゴリズムを1つに固定するのは、JWS でよく知られた取り違え——`alg` を `none` や HMAC に書き換えて、公開鍵を共通鍵として使わせる——を、受け取る側の設定の問題にしないためである。gated は EdDSA でしか署名しないと決めておけば、バックエンドは「EdDSA 以外は捨てる」と書くだけでよい。Ed25519 を選んだのは、鍵も署名も小さく、毎回の要求に付けるヘッダとして軽いからである。

期限を60秒にするのは、アサーションが要求1つのためのものだからである。gated は要求のたびに新しく署名し、使い回さない。期限が要るのは、ログやエラー収集にヘッダが書き出されたときに、拾った値を使える窓を狭めるためである。60秒は、gated とバックエンドの時計のずれと、転送にかかる時間を吸収できる長さとして取る。長く続く要求——ストリーミングや WebSocket——でも、バックエンドが検証するのは要求の始まりの1回なので、期限が要求の長さを縛ることはない。

要求のパスやメソッドはアサーションに入れない。入れれば同じホストの別のパスへの使い回しも防げるが、バックエンドは受け取ったパスと突き合わせる手順を正しく書かなければならず、書き間違えると正当な要求が落ちる。ホストより細かく閉じ込める理由は下に書く。

### ヘッダ名と、クライアントが付けたものを消すこと

ヘッダ名は `Gated-Assertion` とする。`X-` の接頭辞は付けない。

gated は、**転送するすべての要求から、クライアントが付けた `Gated-` で始まるヘッダを消す**。守られた Ingress か否か、主体が決まったか否かを問わない。主体が決まった要求には、消したうえで gated が署名したものを付け直す。

消し忘れた要求が1つでもあれば、そこでは誰でも名乗れる。アサーションは署名されているので、偽物を付けても検証で落ちるはずではある。それでも消すのは、検証が一度でも緩い実装に当たったときに、gated の後ろであることが「gated が付けた値だけが届く」を意味している状態を保つためである。`X-Forwarded-For` をクライアントの申告ごと捨てるのと同じ考え方である（ADR 0013）。

接頭辞ごと消すのは、`/__gated/` のパスを予約したのと同じ理由である（ADR 0018）。あとからヘッダを足すたびに「消す名前の一覧」へ書き足すことにすると、足し忘れた名前が素通しになる。接頭辞を予約しておけば、gated が将来付けるヘッダは最初から守られている。

### 署名鍵はセッションの鍵とは別の非対称の鍵

アサーションに署名する鍵は、セッションの署名鍵（ADR 0003）と別にし、Ed25519 の鍵対とする。

セッションの鍵は共通鍵（HMAC）である。それをバックエンドに配って検証させれば、バックエンドはセッションの Cookie もアサーションも偽造できるようになる。非対称の鍵なら、バックエンドに渡るのは検証にしか使えない公開鍵だけである。バックエンドを1つ乗っ取られても、それで他のバックエンドへ誰かを名乗れるようにはならない。

鍵の保管と共有は、セッションの鍵と同じ形にする（ADR 0006）。

- 鍵は Secret に置く。どの Secret かは起動フラグで指定し、既定を持たない（ADR 0009）。未指定なら起動を拒否する。
- Secret が無ければ、どのレプリカでも新しい鍵を生成して作る。作れるのは最初の1つだけで、全レプリカがそれを読む。既にある Secret は上書きしない（ADR 0035）。当初はリーダーだけが生成していたが、この版へ上げる間に古い版がリーダーのまま残ると誰も鍵を作らず、新しいレプリカが ready にならないまま更新が止まったため改めた。
- 全レプリカが Secret を読み、同じ鍵で署名する。署名鍵を読めていないレプリカは ready にならない。署名できないまま転送すれば、ログイン済みの利用者がバックエンドから未ログインとして扱われる。

Secret の中には、署名に使う鍵を1つと、署名には使わず公開だけする鍵を0個以上置けるようにする。公開だけする鍵は、交換の途中で新旧の両方をバックエンドに知らせておくためにある。

### 鍵の交換は、公開してから署名に使う

鍵の交換は運用者が Secret を書き換えて行う。gated が時刻を見て自動で交換することはしない。セッションの鍵の差し替えと同じく、意図してする操作として扱う。

交換は次の順に行う。

1. 新しい鍵を「公開だけする鍵」として Secret に足す。全レプリカが読み直し、バックエンドが公開鍵を取り直すまで待つ。
2. 新しい鍵を署名に使う鍵にし、古い鍵を「公開だけする鍵」に移す。
3. 古い鍵で署名したアサーションの期限が切れたあとで、古い鍵を Secret から消す。

公開を先にするのは、レプリカが Secret を読み直す時期がそろわないからである。署名の鍵をいきなり替えると、新しい鍵で署名したアサーションが、まだ新しい公開鍵を知らないバックエンドに届き、正当な要求が落ちる。先に公開しておけば、どのレプリカがどちらの鍵で署名していても、バックエンドは検証できる。

署名鍵が漏れた場合は、手順の1を飛ばして2から行い、古い鍵をすぐ消す。そのあいだ一部の要求が落ちることを受け入れる。

### 公開鍵は中央認証ホストの `/__gated/` の下で JWKS として配る

公開鍵は、中央認証ホストの `/__gated/jwks.json` で、JWKS の形で配る。署名に使う鍵と公開だけする鍵の両方の公開鍵を載せる。秘密鍵の情報は載せない。

ここに置くのは、ログインと同じ場所で答えられるからである。ログインのハンドラはルーティング・認可・プロキシより前にあり（ADR 0020）、中央認証ホストの `/__gated/` 以下は gated 自身が答える。Ingress の書き間違いや fail-open の影響を受けない。予約するパスは中央認証ホストの `/__gated/` の下に1つ増えるだけで、他のホストで予約する範囲（`/__gated/callback`）は広げない。

応答には短いキャッシュの期限（5分）を付ける。バックエンドは公開鍵をキャッシュしてよいが、知らない `kid` のアサーションが来たら、間隔を空けたうえで一度取り直す。交換の手順1で待つ時間は、レプリカが Secret を読み直す間隔と、このキャッシュの期限を足したものになる。

ConfigMap で配る案は採らない。ConfigMap は namespace を越えて mount できないので、バックエンドの namespace ごとに gated が書きにいくことになり、gated に広い書き込み権限が要る。URL で配れば、バックエンドはクラスターの中にあっても外にあっても同じ設定で済む。必要になれば、あとから足せる。

### バックエンドが確かめること

バックエンドは、アサーションを要求のたびに次の順で確かめる。どれか1つでも満たさなければ、その要求を未認証として扱う。

1. `Gated-Assertion` ヘッダがあること。無ければ未認証である。
2. JWS の compact 形式として読め、ヘッダの `alg` が `EdDSA`、`typ` が `gated-assertion+jwt` であること。`alg` はアサーションに書かれた値を信じるのではなく、受け付ける値を自分の側で固定しておく。
3. `kid` に当たる公開鍵が、自分の設定に書いた発行元の JWKS にあること。JWKS の URL はアサーションから読まず、自分の設定から取る。知らない `kid` なら一度だけ取り直す。
4. その公開鍵で署名が検証できること。
5. `iss` が自分の設定に書いた発行元と一致すること。
6. `aud` が自分の公開ホスト名と一致すること。比べる相手は自分の設定に書いた名前であって、要求の `Host` ヘッダではない。`Host` は送る側が自由に書けるので、別のホスト宛てのアサーションを `Host` ごと持ち込まれると、`Host` と比べる実装は通してしまう。
7. `exp` が過ぎておらず、`iat` が未来すぎないこと。時計のずれとして数十秒までを許す。
8. `sub` が、自分が許す主体の一覧にあること。

1〜7 が「gated が、このホストについて、この主体を認証した」ことの確認で、8 が「その主体を自分が許す」ことの判断である。gated の `NetworkRole` と同じ主体を書くことになるが、二重に書くのは意図したものである。gated の設定が fail-open になったときにも、8 が残って断る。

### アサーションが閉じ込められるのはホストまで

`aud` はホスト名であり、それより細かくはしない。同じホストの下に、パスで分けた別々のバックエンドが居る場合、一方のバックエンドが受け取ったアサーションを期限内にもう一方へ持ち込めば、同じ利用者として通る。

これは受け入れる。gated はホストを信頼の単位にしている。ADR 0003 がセッションの Cookie を親ドメインに広げずホストに閉じたのは、信用しないアプリケーションを別のホストに置けるようにするためだった。裏を返せば、同じホストに並ぶアプリケーションは、ブラウザから見て同じ Cookie を受け取る、互いに信用しあう間柄である。アサーションもその単位に揃える。Service の名前のような gated の内部の値を `aud` に入れれば狭められるが、バックエンドが自分の Service の名前を設定に持つ必要が生まれ、ホストより壊れやすい。

### 退けた案

**主体を素のヘッダで渡す。** `X-Forwarded-User` や `Remote-User` のように、主体をそのまま書いたヘッダを付ける。実装は最も簡単で、前例も多い。しかしバックエンドがそれを信じてよいのは、gated を通らない要求が届かない場合に限られる。それが成り立たないことが、そもそもの問題である。クラスターの中の Pod は同じヘッダを付けて Service を直接叩ける。

**gated が自分の ServiceAccount の token を付け、バックエンドが TokenReview で確かめる。** 「gated から来た」ことは確かめられ、クラスターの仕組みをそのまま使える。しかし主体は別のヘッダに素のまま載るので、token と主体が結び付いていない。token を受け取ったバックエンドは、それを別のバックエンドへ持ち込み、好きな主体を名乗れる。期限も要求1つよりずっと長い。加えて、バックエンドは要求のたびに API サーバへ問い合わせることになる。

**gated とバックエンドの間を相互 TLS にする。** gated がクライアント証明書を提示し、バックエンドがそれを確かめる。「gated から来た」ことは強く確かめられるが、主体はやはり素のヘッダになり、上と同じく主体の結び付きが無い。さらに、すべてのバックエンドに TLS の終端と証明書の管理を要求する。gated はバックエンドへ平文の HTTP/1.1 で話すと決めており（ADR 0013）、それを覆すほどの利点は無い。

**共通鍵（HMAC）で署名する。** 署名は軽く、セッションと同じ形で実装できる。しかし検証に使う鍵で署名もできるので、鍵を渡したバックエンドは誰でも名乗れる。バックエンドごとに別の鍵を配れば防げるが、gated がバックエンドの一覧と鍵の対応を持つことになる。

**セッションの Cookie や `AccessToken` をそのまま渡す。** バックエンドは gated と同じ方法で主体を確かめられる。しかしそれは、gated に対する資格情報をバックエンドに渡すことであり、ADR 0013 と ADR 0022 が落とすと決めたものそのものである。受け取ったバックエンドは、その利用者として他の保護対象へ入れる。

**Ingress ごとにアノテーションで有効にする。** 必要な Ingress にだけ付けられる。しかし gated はアノテーションを読まない（ADR 0001、ADR 0012）。読まないバックエンドには害が無いので、切り替えの手段を足す理由が無い。

## Consequences

バックエンドが、gated を通らない要求と、gated の設定が fail-open になったときの要求を、自分で断れるようになる。gated の守りとバックエンドの守りが別々に効くので、どちらか一方の設定を誤っても、もう一方が残る。

アサーションを確かめるのはバックエンドの仕事であり、gated はそれを強制できない。確かめないバックエンドにとっては、何も変わらない。この決定が効くのは、確かめると決めたバックエンドだけである。

ログイン済みの要求のすべてに、数百バイトのヘッダが1つ増える。署名は要求のたびに行う。Ed25519 の署名は1回あたりマイクロ秒の単位で、この規模では測れない。

起動フラグが1つ増え、既定を持たない。既存の環境は、版を上げるときにフラグを足さなければ起動しない。足さずに上げると Pod が CrashLoopBackOff になり、ログにフラグ名が出る（ADR 0009）。Secret は gated が作るので、運用者が用意するものは Secret の置き場所の指定だけである。

`Gated-` で始まるリクエストヘッダが gated の予約になる。アプリケーションが同じ接頭辞のヘッダをクライアントから受け取っていれば、それは届かなくなる。

中央認証ホストの `/__gated/jwks.json` が公開の入口になる。中身は公開鍵だけで、誰に読まれても困らない。中央認証ホストが落ちていればバックエンドは公開鍵を取り直せないが、キャッシュしている鍵で検証は続く。中央認証ホストは既にログインの単一障害点であり（ADR 0003）、これで新しい種類の依存が増えるわけではない。

鍵の交換は運用者の手順であり、手順を飛ばすと一部の要求が落ちる。落ちる方向の失敗であって、通ってはいけない要求が通る方向ではない。

主体の閉じ込めはホスト単位なので、同じホストの別々のバックエンドは、互いに受け取ったアサーションを期限内なら使い回せる。互いを信用しないアプリケーションは別のホストに置く、という ADR 0003 の前提がここにも掛かる。
