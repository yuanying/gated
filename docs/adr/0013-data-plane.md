# 0013. データプレーンの作り

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0001 はコントローラとリバースプロキシを単一プロセスに同居させ、外部のデータプレーンを持たないと決めた。既製品が引き受けていたものをすべて自分で背負うことになる、とも書いてある。

背負う中身のうち、決めておかないと後戻りが高くつくものがいくつかある。バックエンドをどこまで自分で解決するか、転送するリクエストに何を足して何を落とすか、ルーティングテーブルをどう差し替えるか、TLS の証明書をどこから読むか、そして 80 番と 443 番がそれぞれ何をするかである。

このうちいくつかは正しさに直結する。転送ヘッダを間違えればバックエンドはクライアントのアドレスを取り違え、テーブルの差し替えを間違えれば処理中のリクエストが途中で別の設定に切り替わる。

## Decision

### バックエンドは Service の cluster IP へ転送する

Ingress のバックエンドは Service と port である。それを Service の cluster IP と port 番号に解決し、そこへ転送する。EndpointSlice は見ない。

kube-proxy が既に ready な endpoint へ分散している。同じことをここでやり直すには、EndpointSlice の追跡と readiness とトポロジの扱いが要り、辿り着く答えは同じである。headless Service と ExternalName Service は転送先が無いので設定の誤りとして扱う。

### 転送ヘッダはクライアントの申告を捨てる

`X-Forwarded-For` / `X-Forwarded-Proto` / `X-Forwarded-Host` には、gated 自身が観測した値だけを入れる。クライアントが送ってきた同名のヘッダは引き継がない。

gated はエッジに立つ。クライアント由来の `X-Forwarded-For` は自分のアドレスについての自称であり、これを引き継ぐとバックエンドのアクセス制限やレート制限を任意のアドレスから騙せる。ホップバイホップヘッダは `net/http` の扱いに委ね、往復のどちら向きも透過させない。

`Host` はクライアントが使った名前のまま渡す。絶対 URL を組み立てるアプリケーションと、`Host` でバーチャルホストするアプリケーションはこれを必要とする。

### テーブルは丸ごと差し替える

ルーティングテーブルは不変のスナップショットとして作り、atomic なポインタの入れ替えで反映する。差分更新はしない。

処理中のリクエストは、経路が決まったときのテーブルのまま最後まで走る。数分続くストリーミングの最中に別の Ingress が適用されても影響を受けない。リクエスト処理側はロックを取らない。

差分更新にしないのは、削除・改名・部分的な失敗を取りこぼしたときに、元の Ingress より長生きする経路が残るためである。クラスター1つ分の Ingress を作り直す費用は、その危険に比べて無視できる。

### 一致しなければ 404、届かなければ 502

どの経路にも一致しないリクエストは 404 とする。最初のスナップショットが入る前も同じく 404 である。バックエンドを解決できない、あるいは応答しない場合は 502 とする。設定が無いことと、設定はあるが相手が居ないことを、応答の上で区別する。

### 80 番はバックエンドへ転送しない

平文のリスナがすることは2つだけである。`/.well-known/acme-challenge/` に自分で答えるか（ADR 0005）、それ以外を HTTPS へ 308 で送るかのどちらかで、バックエンドへは決して転送しない。平文のリクエストがバックエンドに届く経路を持たない。

301 ではなく 308 を使う。301 は POST を GET に変えてしまい、リクエストが静かに失われる。

チャレンジのトークンが見つからない場合は 404 であって、リダイレクトではない。リダイレクトすると、証明書がまだ無いホストへ検証サーバを送ることになり、そこで確実に失敗する。

チャレンジに答える仕組みは interface として切り、この段階では未設定＝常に 404 とする。実体は証明書発行の段階で入る。

### TLS は SNI で選び、無ければハンドシェイクを失敗させる

証明書は `spec.tls` が指す `kubernetes.io/tls` Secret から読む（ADR 0005）。SNI の名前に対して証明書を持たない場合はハンドシェイクを失敗させる。

別のホストの証明書を返すという選択肢もあるが、そうすると「設定が足りない」という事実が「subject が違う」というブラウザの警告として現れる。原因まで戻るのが難しくなるだけで、得るものが無い。

Secret は informer 経由で読む。リーダーが書き換えた証明書（ADR 0006）が再起動なしに反映される。パースの結果は Secret の resourceVersion が変わるまで再利用する。ハンドシェイクのたびに PEM を読み直す必要は無い。

### Secret のキャッシュは TLS 型に限る

informer が保持する Secret は `type=kubernetes.io/tls` のものだけに絞る。全 Secret をキャッシュすると、クラスター中の資格情報をこのプロセスのメモリに置くことになる。

その代わり、manager の client は Secret をキャッシュから読まない設定にする。絞ったキャッシュを経由すると、Opaque な Secret が「存在しない」と答えられてしまい、後続の段階が踏む罠になる。

### HTTP/2 は ALPN で有効にする

TLS のリスナは `h2` と `http/1.1` を広告する。アップグレードは HTTP/2 には存在しないが、WebSocket を張るクライアントはその接続について `http/1.1` を選ぶため、両立する。

## Consequences

バックエンドの選択を kube-proxy に委ねたことで、EndpointSlice の watch もヘルスチェックも持たずに済む。代償として、gated から見えるのは「Service が居るかどうか」までで、その先の endpoint が全滅していれば 502 が返るだけになる。どの Pod が落ちているかは gated のログには出ない。

転送ヘッダを信用しない方針は、gated の前段にロードバランサが居てそれが `X-Forwarded-For` を付けている場合、クライアントの本来のアドレスが失われることを意味する。前段を信用する設定は今回持たない。必要になった時点で、信用するアドレス範囲を明示させる形で足す。

テーブルを丸ごと差し替えるため、Ingress が1つ変わるたびに全件を読み直して作り直す。この規模では問題にならないが、Ingress が数千に増えれば見直しが要る。

80 番から一切転送しないことで、HTTPS へのリダイレクトを望まない経路は表現できない。ADR 0008 が挙げた移行対象のアノテーションのうち SSL リダイレクトの無効化がこれにあたるが、対象が無いため実装しない。

タイムアウト、リクエストボディの上限、バックエンドごとの調整は、いずれもまだ持っていない。ingress-nginx のアノテーションで設定していたものが該当する。必要になった時点で、Ingress のアノテーションではなく独立した表現として足すことになる（ADR 0001）。
