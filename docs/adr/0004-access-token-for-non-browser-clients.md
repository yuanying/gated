# 0004. 非ブラウザクライアントの認証: AccessToken

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0003 の認証はブラウザのリダイレクトを前提としている。しかし保護対象には、ブラウザを持たないクライアントからアクセスされるものがある。

最も分かりやすいのは Docker registry である。現在は BASIC 認証で保護されており、`docker login` でユーザー名とパスワードを渡している。これを OIDC のリダイレクトに置き換えることはできない。`docker push` の途中でブラウザが開くわけにはいかない。

同様の問題は `curl` での API 呼び出しや、クラスター内から監視系がエンドポイントを叩く場合にも起きる。BASIC 認証を全廃するなら、これらの経路に代わる手段が必要である。

## Decision

`AccessToken` CRD を `gate.unstable.cloud` に定義する。特定の主体に紐付いた長命のトークンを発行する仕組みである。

`AccessToken` は「どの主体として振る舞うか」を宣言する。コントローラがトークンの実体を生成して Secret に書き込み、その参照を `status` に返す。トークンそのものを人が書くことはない。

トークンは2つの経路で受け付ける。

| 経路 | 用途 |
|---|---|
| `Authorization: Bearer <token>` | `curl` や API クライアント |
| BASIC 認証のパスワード欄 | `docker login` など、BASIC 認証しか話せないクライアント |

BASIC 認証のパスワード欄でも受け付けるのは、Docker クライアントを変更せずに移行するためである。プロトコルとしては BASIC 認証の形をしているが、渡しているのは共有パスワードではなく個人に紐付いた失効可能なトークンであり、性質はまったく異なる。

トークンで認証されたリクエストは、`AccessToken` が宣言する主体として扱われる。認可の判定はブラウザ経由のリクエストとまったく同じ経路を通り、`NetworkRole` / `NetworkRoleBinding` で評価される。入口が2つあるだけで、認可の仕組みは1つである。

Kubernetes の ServiceAccount トークンを `TokenReview` で検証する案も検討したが、主たる用途である手元の `docker login` に使いにくいため採らなかった。将来クラスター内からのアクセスに必要になれば、主体の種類として追加できる。

## Consequences

BASIC 認証を全廃しつつ Docker registry を使い続けられる。クライアント側の設定は `docker login` のパスワードをトークンに差し替えるだけで済む。

トークンが個人に紐付くため、共有パスワードと違って、失効させても他の利用者に影響しない。用途ごとに別のトークンを発行しておけば、漏洩時に影響範囲を限定できる。

Cookie セッションと違い、トークンは即座に失効できる。`AccessToken` を削除すればそのトークンは次のリクエストから通らなくなる。

トークンは長命であり、その値は Secret に平文で存在する。Secret を読める者はトークンを持つ者と等価になるため、Secret へのアクセス権が実質的な認可の抜け道になる。名前空間の分離と RBAC で守る必要がある。

BASIC 認証のパスワード欄でトークンを受け付けるということは、認証ヘッダを見ただけでは「BASIC 認証を使っている」ように見えるということである。移行後に「まだ BASIC 認証が残っている」と誤解しないよう、実装とドキュメントで明示する。

トークンをどこまで細かく発行するか、有効期限をどう扱うかは実装時に決める。少なくとも `status` に最終使用日時を記録し、使われなくなったトークンを見つけられるようにする。
