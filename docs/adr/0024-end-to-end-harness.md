# 0024. E2E は自分でクラスターを作り、認証局も Identity Provider もその中に置く

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0007 は E2E を「kind + Pebble + モック IdP で、ゴールの4項目に対応するシナリオに絞る」と決めた。決めていないのは、それをどう組み立てるかである。

組み立て方には具体的な困りごとが3つある。

1つ目は名前である。ACME で証明書を取るには、認証局がホスト名を解決してそこへ検証のリクエストを送れなければならない。テストが使うホスト名は誰のものでもなく、どの DNS にも載っていない。

2つ目は、テストプロセスがクラスターの外に居ることである。テストはブラウザの役を演じる。ログインの途中でブラウザは Identity Provider へ飛ばされるので、テストからも Identity Provider に届く必要がある。しかし gated 自身もサーバ間の通信で同じ Identity Provider を呼ぶ。両者が同じ1つの URL を使えなければならない。

3つ目は、ゴールの4番目——複数レプリカ——が「どのレプリカに届いても答えられる」という主張であることである。Service 越しに何度か叩いて確かめる形にすると、どのレプリカが答えたかはクラスターの気分次第になる。確かめたはずのものが確かめられていない。

## Decision

### クラスターの生成から破棄までをテストが持つ

`make test-e2e` が kind クラスターを作り、イメージを組み立てて読み込み、manifest を適用し、シナリオを回し、最後に壊す。途中で人手が要る箇所を作らない。kind は controller-gen などと同じく `go.mod` の tool ディレクティブで固定するので、事前のインストールも要らない（ADR 0011）。

デバッグのために `GATED_E2E_KEEP_CLUSTER` が設定されていればクラスターを残す。既定は残さない。

### 認証局とその DNS をクラスターの中に置き、全ての名前を gated へ向ける

Pebble と、Pebble が引く DNS サーバ（pebble-challtestsrv）をクラスター内に置く。DNS サーバは**どの名前に対しても gated の Service の cluster IP を返す**。これで、誰のものでもないホスト名に対する HTTP-01 の検証リクエストが gated に届く。本物の Let's Encrypt にも本物の DNS にも触れない（ADR 0007）。

そのために cluster IP を2つ、manifest に直接書く。DNS サーバは Service が作られる前に設定されるので、後から読んだ値を渡すことができないからである。kind の設定で service subnet を明示し、その中の値を使う。これはテストが自分で作るクラスターの内部の取り決めであり、運用環境の情報ではない。

gated は ACME ディレクトリの TLS 証明書を他のサーバと同じように検証する。検証を切る設定は入れない——切ってしまうと、切れていることに誰も気づけない。代わりに Pebble のイメージが持つ認証局を ConfigMap に写し、`SSL_CERT_FILE` で gated に渡す。Service の名前を `pebble` にしてあるのは、その証明書が名乗る名前がそれだからである。

### テストは名前を書き換えず、接続先だけを書き換える

テスト側の HTTP クライアントは、リクエストの中のホスト名はそのままに、接続先だけを kind が公開したポートへ差し替える。こうすると、TLS が検証する名前も、gated がルーティングに使う名前も、認可の判定に渡る名前も、本来のホスト名のままになる。ホスト名を書き換えてしまうと、そこが検証対象から抜け落ちる。

同じ仕組みで、Identity Provider のクラスター内 DNS 名がテストからも引ける。gated が使う URL とブラウザが飛ばされる URL が同じ1つになり、OAuth アプリケーションの登録と同じ形になる。

Identity Provider は GitHub の OAuth の受け答えを模す。誰としてログインするかはテストがヘッダで指示する。本物の provider は訪問者に尋ねるが、ここでは訪問者がテストである。

### レプリカを名指しで確かめる

「どのレプリカでも答えられる」は、レプリカを名指しして確かめる。リーダーが書くのと同じ形でチャレンジを共有 Secret へ置き、各 Pod へ直接トンネルを開いて、**すべての Pod が**答えることを確かめる。Service 越しでは、答えたのがどのレプリカかが分からない。

「発行が重複しない」は Lease の保持者が1つであることと、証明書を注文したログを持つレプリカが1つであることで確かめる。

### シナリオを増やさない

E2E で確かめるのはゴールの4項目に対応するものだけである。パスのマッチング、主体の網羅、更新の要否といったものは純関数のテーブルテストが持つ（ADR 0007）。E2E で網羅しようとすると、実行時間が伸びる一方で、失敗したときにどの層が悪いのか分からなくなる。

E2E がここにある理由は網羅ではなく継ぎ目である。純関数は正しいのに、そこへ渡す入力の組み立てが間違っている、という失敗は、単体テストにも envtest にも見えない。

## Consequences

`make test-e2e` は数分かかる。イメージのビルド、クラスターの生成、証明書の発行がそれぞれ時間を使う。日常の開発ループには乗せない（ADR 0007）。

manifest に cluster IP が2つ書かれる。kind の設定にある service subnet と対応が取れていなければならず、片方を変えたらもう片方も変わる。テスト専用のファイルの中に閉じている。

E2E はイメージを組み立てるので、`Dockerfile` が壊れていれば E2E が落ちる。イメージの組み立て方も検証対象に入ったということであり、これは望ましい。

Pebble の公開イメージは複数プラットフォームのマニフェストリストであり、kind の読み込みが受け取らない。1行の Dockerfile を経由して単一プラットフォームに焼き直している。中身は変えていない。
