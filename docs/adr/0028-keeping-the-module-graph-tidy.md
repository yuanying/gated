# 0028. `go mod tidy` が通る状態を CI で守る

- Date: 2026-08-22
- Status: Accepted

## Context

依存を1つ足そうとしたときに、`go mod tidy` がこう言って何も書かずに止まることが分かった。

同じパッケージを2つのモジュールが提供しており、どちらから取るべきか決められない、という
種類の失敗である。片方は分割される前の大きなモジュール、もう片方は分割後の小さなモジュール
だった。前者を要求していたのは、直接の依存ではなく lint のツールチェインの奥にある古い
ライブラリである。

この状態はしばらく前から続いていた。表に出なかったのは、誰も `go mod tidy` を回していな
かったからである。CI（ADR 0026）は build・vet・lint・テスト・生成物の再現性を見ていたが、
モジュールグラフが健全かどうかは見ていなかった。

実際に困ったのは、Renovate が Kubernetes の依存を上げた PR で、上流が新しいモジュールを
経由し始めたために `go.sum` のエントリが足りなくなったときである。本来なら `go mod tidy` で
済む場面だったが、その `tidy` が動かないため、欠けているものを名指しで足すしかなかった。
道具が壊れていることに、道具が必要になって初めて気づいた形である。

## Decision

### グラフの曖昧さを解消する

曖昧さの原因になっていたモジュールを、分割後のものが選ばれるところまで引き上げる。
結果として `go.mod` には分割後のモジュールが指定として現れ、古い方は選ばれなくなる。

この変更でグラフの整理が進み、`tidy` はいくつかの指定を書き直した。中でも
`k8s.io/apiextensions-apiserver` が間接から直接へ移った。これは実際にコードが import して
いるものが、そう記録されていなかったということであり、修正である。

### `go mod tidy` を CI の検査にする

`tidy` を走らせ、`go.mod` と `go.sum` に差分が出たら落とすジョブを足す。

見ているものは2つある。1つは、コミットされている `go.mod` と `go.sum` が `tidy` の結果と
一致していること。もう1つは、**`tidy` がそもそも完走すること**である。グラフが再び曖昧に
なれば `tidy` は差分を出す前に失敗するので、同じジョブが両方を捕まえる。

生成物の再現性を見るジョブ（ADR 0011）と同じ考え方である。リポジトリにコミットされている
ものは、道具を回せば再現できなければならない。違いは、こちらが守っているのが成果物ではなく
**道具が使える状態そのもの**だという点にある。

## Consequences

依存を足す作業が普通の作業に戻る。`go mod tidy` を回せばよく、欠けているものを人が名指しで
足す必要はない。

グラフの曖昧さは、次に起きたときには PR の時点で赤くなる。今回のように、必要になってから
気づくことはなくなる。

代償として、依存を引き上げる PR が `tidy` の結果を含んでいないと落ちるようになる。Renovate が
出す PR も例外ではない。落ちた PR は `make tidy` を回して結果を載せれば通るが、その一手間は
増える。曖昧さに気づかないまま進むことに比べれば安いと判断する。

ジョブが1つ増え、モジュールグラフ全体をダウンロードする時間がかかる。ほかの重いジョブと
並列に走るので、全体の待ち時間は変わらない。
