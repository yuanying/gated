# 0016. リース限定を既定にせず、離脱を明示させる

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0006 は責務をレプリカごとに分けた。watch・プロキシ・認証・認可は全レプリカ、ACME による証明書の取得・更新はリーダーのみである。決めていないのは、その分け方をプロセスの中でどう表現し、どう守るかである。

守り方が問題になるのは、使っている controller-runtime の既定が ADR 0006 の表と逆を向いているからである。manager に登録した runnable は、自分から「リースは要らない」と言わない限りリーダー限定になる。つまり全レプリカで動くべきものほど、明示的な宣言を必要とする。

この向きの食い違いは、書き忘れという形で入り込む。実際、段階2と段階3の実装ではルーティングコントローラとキャッシュのウォームアップが何も宣言しておらず、どちらもリーダーのものになっていた。リーダーを取れなかったレプリカはルーティングテーブルを一度も作らず、届いたリクエストすべてに 404 を返す。コメントには「全レプリカで動く」と書かれており、コードはその逆をしていた。

この誤りはレプリカが1つなら見えない。リーダー選出を切ったテストでも見えない。単体テストは1プロセスで動くので、やはり見えない。見えるのは、リーダー選出を有効にしたまま2つ以上のレプリカを動かしたときだけである。

## Decision

### 全レプリカで動くものは、そう明示する

データプレーン側の runnable は、リースを必要としないことを一つ残らず自分で宣言する。既定がどちらであっても意味が変わらない書き方にし、「宣言していないので既定で全レプリカ」という状態を作らない。

逆にリーダー限定であるべきもの——証明書の取得・更新——も、既定に乗っているだけという状態にはせず、そこがリーダーの担当であることをコメントと後述の検査で固定する。

### 分け方は登録経路の性質として検査する

manager へ登録された runnable を列挙し、データプレーンを組み立てる経路が登録したものはすべてリース不要、証明書を組み立てる経路が登録したものはすべてリース必須であることを検査する。

検査の対象を「今ある runnable の名前の一覧」にはしない。一覧は、新しい runnable が足されたときに更新されないことでしか壊れず、それは今回の書き忘れと同じ性質の誤りである。登録経路ごとの性質として書けば、段階5以降で認可やトークンのコントローラを足したときにも自動的に対象になる。

### レプリカ2つの envtest を持つ

上の検査は登録のされ方しか見ない。実際にフォロワーがルーティングテーブルを作り、トラフィックを流し、リーダーが取得した証明書で TLS を終端することは、リーダー選出を有効にした2レプリカの envtest で確かめる。assertion はフォロワー側に置く。リーダー側は単一レプリカのテストが既に見ている。

リーダーを落とす際はリースを返させない。退避された Pod も、OOM で殺された Pod も、分断された Pod もリースを返さない。返さずに落とすことで「リーダーが誰も居ない時間」が実際に生まれ、その間もトラフィックが流れ続けることを測れる。リースを返して落とすと後任が即座に決まってしまい、測りたかった時間が存在しなくなる。

## Consequences

データプレーンに runnable を足すたびに、リースが要らないという一行の宣言が要る。忘れれば検査が落ちる。ADR 0006 の表がコードの中に一箇所だけ書かれた文章ではなく、登録のたびに問われる性質になる。

検査が登録経路の性質である以上、runnable が増えても検査は書き換えなくてよい。書き換えが要るのは、ADR 0006 の表そのものを変えるときだけである。

2レプリカの envtest はリースの満了を待つため数秒かかる。envtest は明示的に実行する層であり日常の開発ループには乗らない（ADR 0007・0011）ので、この数秒は許容する。

リーダー選出そのものを切って動かした場合、この分け方は何の意味も持たない。全レプリカがリーダーとして振る舞い、証明書の取得も各レプリカが行う。単一レプリカで動かす場合にだけ意味のある構成であり、複数レプリカで選出を切ることは想定しない。
