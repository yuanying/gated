# 0022. トークンをどう受け取り、どう照合するか

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0004 は `AccessToken` を定義し、`Authorization: Bearer` と BASIC 認証のパスワード欄の2経路で受け付けること、コントローラがトークンの実体を生成して Secret に書くこと、最終使用日時を記録することを決めた。決めていないのは、その3つをどう実装するかである。

決めておかないと後戻りが高くつくものがいくつかある。BASIC 認証のユーザー名欄をどう扱うか。プロキシが提示されたトークンを何と突き合わせるか。照合したトークンをバックエンドへ渡すのか捨てるのか。最終使用日時をどれだけの頻度で書くのか。そして Secret が消えたときに何が起きるかである。

このうち照合の相手は ADR 0013 と直接ぶつかる。あちらは informer が保持する Secret を `type=kubernetes.io/tls` のものだけに絞ると決めた。全 Secret をキャッシュすればクラスター中の資格情報をこのプロセスのメモリに置くことになるためである。トークンの実体は `Opaque` Secret にあるので、素直に「Secret を読んで比べる」実装はその決定を覆すことになる。

## Decision

### プロキシは status のダイジェストと照合する

`AccessToken` の `status.tokenHash` にトークンの SHA-256 を hex で書き、プロキシはその集合だけを持つ。Secret は読まない。

ダイジェストは、提示されたトークンを認識するには十分で、トークンを作り出すには足りない。これによって、リクエスト経路が持つのは「どのトークンが有効か」という情報だけになり、トークンそのものはクラスター中のどの Secret より広く読める場所には出てこない。ADR 0013 の絞り込みを緩めずに済む。

代償として、ダイジェストは `status` にあるぶん Secret より広く読める。したがって**ダイジェストを提示しても通ってはならない**。照合は提示された値を改めてハッシュしてから行い、提示された値そのものをダイジェストと比べる経路は持たない。

照合は定数時間で行い、最初に一致した時点で打ち切らない。集合の全要素と比べ切ってから答える。比較しているのが既にダイジェストである以上、時間差から漏れるのは「どのトークンに近かったか」であって元の値ではないが、それを漏らす理由も無い。

`status.tokenHash` が無い、ダイジェストの形をしていない、主体が空、主体が `system:` で始まる——これらの要素は集合を組み立てる時点で捨てる。リクエスト経路に判断を残さないためである。`system:` の除外は CRD のスキーマ（ADR 0010）が入場時に拒否しているものの2つ目の錠であり、スキーマが緩んだ場合や古いオブジェクトが残っていた場合に効く。

### BASIC 認証のユーザー名欄は読まない

パスワード欄だけをトークンとして読む。ユーザー名欄は検証もせず、資格情報としても受け付けない。

`docker login` はユーザー名を要求するので、何かを入力させることは避けられない。そこに意味を持たせる案は3つあった。固定の名前を要求する、`spec.subject` と一致することを要求する、何も見ない、である。

前の2つを採らないのは、どちらも**認証の強度を上げずに失敗経路だけを増やす**ためである。トークンを持つ者は主体名も知っている（`AccessToken` を読めば書いてある）か、あるいは総当たりで済む長さの文字列を当てるだけでよい。守りは1つも増えない。一方で、名前が違うだけで拒否されたときの応答は「パスワードが違う」場合と区別がつかず、`docker login` の出力からは原因に戻れない。主体名を要求する案にはもう一つ問題がある。GitHub のログイン名が変わったときにトークンが黙って通らなくなり、その理由がどこにも出ない。

ユーザー名欄をもう一つの入口にする——ユーザー名にトークンを書いても受け付ける——案も採らない。1つのスキームに入口は1つとし、「何が提示されたか」を一意にする。

結果としてユーザー名欄は記録用の文字列になる。`docker login` はこれを設定ファイルに残すので、複数のトークンを使い分けるときの覚書としては機能する。gated はそれを読まない。

### 照合できたトークンはバックエンドへ渡さない

`Authorization` ヘッダの中身が gated の発行したトークンであった場合、そのヘッダを落としてから転送する。gated が知らない資格情報——別のトークン、普通の BASIC パスワード、他のスキーム——はそのまま通す。

落とすのは、それが gated に対する資格情報であってバックエンドに対するものではないからである。転送すると、プロキシの後ろにあるものは誰でも、そのトークンを提示してきた人物として他の保護対象へアクセスできるようになる。バックエンドは既に「そこへ転送してよい」と信じられてはいるが、「その利用者になりすましてよい」とまでは信じていない。

知らない資格情報を残すのは、自前で認証しているバックエンドが動き続けるためである。gated が消費しなかったものは gated のものではない。

なおセッション Cookie は現状そのまま転送される。同じ性質の問題を持つが、Cookie の落とし方はブラウザ向けアプリケーションの挙動に影響しうるので、別に決める。

### 最終使用日時は緩衝してから、間隔を空けて書く

リクエスト経路は「このトークンが使われた」をメモリ上の緩衝に置くだけにし、API サーバへの書き込みは別のループが行う。緩衝はトークンごとに1つの時刻しか保持しないので、1分間に千回使われたトークンも書き込みは1回である。

書き込む前に、既に記録されている時刻と比べる。差が既定の1分未満なら書かない。この比較を「このレプリカが最後に書いた時刻」ではなく「オブジェクトに入っている時刻」に対して行うので、複数のレプリカが同じトークンを見ていても書き込みの総量はおおむね1分に1回に収まる。

書き込みに失敗したものは捨てて、やり直さない。書こうとしている値は「最近使われた」であって、次に使われたときにはより新しい値が生まれる。古い値を抱えて再送するのは、より悪い答えのための仕事である。

この記録は「まだ使われているか」を答えるためのもので、精度は日の単位で足りる。ADR 0004 が求めているのも、使われなくなったトークンを見つけられることだけである。

最終使用日時を書くのは**リーダーではなく、そのリクエストを処理したレプリカ**である。使われたことを知っているのはそのレプリカだけで、リーダーへ伝える経路は無い（ADR 0006 はレプリカ間の直接通信を持たないと決めている）。

### Secret が消えたらトークンを作り直す

`spec.secretName`（既定は `AccessToken` 自身の名前）の Secret に既にトークンがあれば、それを使い続ける。Secret が無ければ新しいトークンを生成して書く。

Secret を消してトークンを作り直せる、というのが運用上の唯一の rotate 手段になる。ダイジェストから元の値は復元できないので、消えた Secret を「元通りに」することはできず、新しい値を作る以外の選択肢が無い。

Secret は `AccessToken` を owner に持つ。`AccessToken` を消せば Secret も消える。ADR 0004 の「削除すれば次のリクエストから通らなくなる」を成立させているのは実際には status の集合の側だが、資格情報が書かれた Secret だけが残り続けるのは望ましくない。

Secret が既に存在し、そこに gated のトークンが無く、gated が作ったものでもない場合は、**何も書かずに condition を False にする**。`spec.secretName` が既存の Secret とぶつかったときに黙って上書きすると、誰かの資格情報が消える。gated が作ったかどうかは `app.kubernetes.io/managed-by` ラベルで見る（ACME の Secret と同じ）。中身が空の Secret は壊すものが無いので書き込む。

トークン Secret は watch できない。informer が TLS 型しか持たないためである（ADR 0013）。そのため `AccessToken` は10分ごとに見直す。Secret を消してから作り直されるまでの遅れはこの間隔になる。

### 生成と照合でレプリカの役割を分ける

| 責務 | 実行するレプリカ |
|---|---|
| トークンの生成と Secret への書き込み、`tokenHash` の書き戻し | リーダーのみ |
| 有効なトークンの集合の構築 | 全レプリカ |
| トークンの照合と認可 | 全レプリカ |
| `lastUsedTime` の書き戻し | 全レプリカ |

トークンは導出される値ではなく発明される値なので、2つのレプリカが決めれば2つできて、後から書いたほうが先のものを失効させる。生成はリーダーに限る（ADR 0006）。

### 認可の経路は分岐させない

トークンで確定した主体は、セッション Cookie で確定した主体とまったく同じ場所に入る。主体を答えるものを順に尋ねて最初の答えを採る、という並びがあるだけで、その先の判定は入口を知らない。

尋ねる順はトークンが先である。トークンは意図して提示されるが、Cookie はブラウザが勝手に送るためである。両方が付いたリクエストでは、意図したほうを信じる。

## Consequences

`docker login` はユーザー名に何を入れても通る。移行の説明が「パスワード欄にトークンを入れる、ユーザー名は何でもよい」の一行で済む一方、「ユーザー名が合っているから大丈夫」という誤解は生まれうる。ドキュメントで、あれが認証に使われていないことを明示する。

BASIC 認証の形で受け付ける以上、ネットワーク上を流れるものは BASIC 認証に見える。ADR 0004 が警告した「まだ BASIC 認証が残っている」という誤読は、実装を見ても解消しない。名前と文書で区別を維持するしかない。

ダイジェストで照合する設計は、`status` を読める者が「あるトークンが有効かどうか」を知れることを意味する。手元にトークンがあれば、それがどの `AccessToken` のものか照合できる。トークンを持たない者には何も分からない。

最終使用日時は最大で1分ずれ、シャットダウン時に取りこぼす可能性がある（停止時に一度だけ掃き出すが、そこで失敗すれば失われる）。「いつ使われたか」を監査に使うことはできない。監査が必要になれば、それは status ではなくアクセスログの仕事である。

`AccessToken` を10分ごとに見直すため、トークンが1つもなくても定期的な API サーバへの読み取りが発生する。数が数百に増えれば見直しが要る。

照合を全要素の走査にしたので、トークンの数に比例した時間がリクエストごとにかかる。32 バイトの比較が数十回であり、この規模では測れない。数千に増えれば、ダイジェストで引いてから定数時間比較する形に変える余地がある。
