# 0031. 可観測性: アクセスログとメトリクス

- Date: 2026-08-22
- Status: Accepted

## Context

gated はクラスターの入口である。インターネットに面した 80/443 を持ち、すべての HTTP
リクエストがここを通る。にもかかわらず、通ったリクエストの記録が無い。

いま出ているのは、拒否とログイン誘導の `V(1)` ログ（既定では出ない）と、証明書の発行・
更新に関する Event だけである。したがって「昨夜どのアドレスがどのホストの何を何回叩いたか」
にも「この証明書はいつ切れるのか」にも答えられない。Event は既定で1時間で消えるので、
「更新に失敗し続けている」という、自分で証明書を発行するコントローラにとって最も知りたい
状態が、気づかれないまま過ぎていく。

ADR 0002 が受け入れた fail-open の穴も同じ形をしている。`targetRef` が解決できない
`NetworkRole` は何も保護しない。つまり保護しているつもりの Ingress が無認証で公開される。
`status` と Event には出るが、どちらも「見に行った人だけが気づく」経路であり、alert には
できない。

一方で、エッジのログは書いた内容そのものが漏洩になりうる。gated のログイン経路は、完了した
ログインをブラウザへ渡す一度きりのトークンをクエリ文字列に載せる（ADR 0003、ADR 0020）。
アクセスログに URL を丸ごと書けば、そのトークンがログに残る。セッション Cookie と
`Authorization` ヘッダも同様である。「全部書いておけば後で困らない」は、ここでは成り立たない。

## Decision

アクセスログとメトリクスを入れる。どちらも既定で有効にする。どこで動かしても同じ意味を持つ
値であり、ADR 0009 の区分では既定を持ってよい側にあたる。

### アクセスログ

1リクエスト 1 行の構造化ログとして、`Info` レベルで出す。項目は次のとおり。

| 項目 | 内容 |
|---|---|
| クライアントアドレス | 接続元のホスト部（ポートは落とす） |
| メソッド | |
| ホスト | リクエストの `Host` |
| パス | **クエリ文字列を除いたパス** |
| ステータス | 応答したステータスコード。Upgrade が成立した接続は 101 |
| バイト数 | 本体としてクライアントへ書いた量 |
| 所要時間 | ハンドラに入ってから出るまで |
| 主体 | 認可が通った際に名指した主体。無ければ空 |
| Ingress | ルーティングが選んだ Ingress の namespace と name |
| プロトコル | `HTTP/1.1` / `HTTP/2.0`、Upgrade が成立していれば `ws` |
| 上流エラー | 502 で終わったか |

書かないものを決めておく。

- **クエリ文字列**。ログインの受け渡しトークンが乗る唯一の場所であり、そこだけを削るより
  クエリ全体を落とすほうが、後から項目が増えたときに壊れない
- **`Authorization` ヘッダ**と**`Cookie` ヘッダ**。前者にはアクセストークンが、後者には
  セッションが入っている。どちらもそのまま資格情報である
- リクエスト／応答のヘッダ一般。上の2つを除いても、書けば「何を書いてよいか」を
  ヘッダが増えるたびに考え直すことになる

置き場所は、ログインの経路も含めた**一番外側**にする。`/__gated/` 配下は gated 自身が
答えるので、ルーティングの内側に置くと記録から漏れる。ここに置いてもクエリ文字列は
書かないので、受け渡しトークンはログに出ない。

`--access-log=false` で切れる。切ってもメトリクスは出る。

クライアントアドレスとして記録できるのは gated が接続を受けた相手であって、必ずしも
本当のクライアントではない。ロードバランサーが送信元アドレスを書き換える構成では、
記録に残るのは書き換え後のアドレスになる。これは配備側の設定で決まることであり、
gated 側で補正はしない（クライアントの申告するヘッダを信じないという ADR 0013 の決定と
同じ理由による）。

### メトリクス

controller-runtime が既に持っている registry に載せる。エンドポイントとポートは今のまま
であり、増やさない。

| 名前 | 種類 | ラベル |
|---|---|---|
| `gated_http_requests_total` | counter | `ingress_namespace`, `ingress_name`, `method`, `code` |
| `gated_http_request_duration_seconds` | histogram | `ingress_namespace`, `ingress_name` |
| `gated_upstream_errors_total` | counter | `ingress_namespace`, `ingress_name` |
| `gated_certificate_not_after_timestamp_seconds` | gauge | `namespace`, `secret`, `host` |
| `gated_certificate_renewal_failures` | gauge | `namespace`, `secret` |
| `gated_networkrole_target_resolved` | gauge (0/1) | `namespace`, `name` |

ラベルに入れないものを決めておく。

- **パス**。値の種類に上限が無い。1つの Ingress に届く URL の数だけ時系列が増える
- **クライアントアドレス**と**主体**。同じ理由に加えて、メトリクスはログより長く保存される。
  「誰がいつ何を叩いたか」を保持したいならログの仕事である
- **ホスト名**。ただし証明書の2つは例外とする。証明書はホストに対して発行されるもので、
  期限を見るときに知りたいのはホストである。数は Ingress の数で頭打ちになる

Ingress の namespace と name をラベルにするのは、それが有限であり、かつホスト名の代わりに
なるからである。ルーティングが選んだ Ingress を持たないリクエスト（どこにも一致しなかった
もの、ログインの経路そのもの）では、この2つのラベルは空になる。

#### リーダーだけが出すもの

証明書の2つと `NetworkRole` の1つは、reconcile する側が持っている情報から出す。
その reconcile はリーダーだけが行う（ADR 0006）ので、**リーダーでないレプリカではこの3つが
出ない**。これは欠損ではなく、担当していないものについて黙っているだけである。

したがって alert はレプリカをまたいで最大値／最小値を取る形で書くことになる。全レプリカが
同じ値を報告するようにする案（＝全レプリカに reconcile させる）はとらない。ADR 0006 が
リーダーに寄せた理由がそのまま当てはまる。

#### 消えたものは消す

gauge は放っておくと「最後に見た値」を出し続ける。証明書の Secret が消えたのに期限だけが
残れば、いずれ「期限切れが迫っている」と鳴り続ける。`NetworkRole` が消えたのに
「解決できていない」が残れば同じことが起きる。対象が消えたときはその時系列を削除する。

#### 502 の数え方

`gated_upstream_errors_total` はエッジで観測した 502 を数える。gated 自身がバックエンドに
到達できずに返した 502 と、バックエンド自身が返した 502 を、いまは区別しない。区別するには
転送の内側に印を置く必要がある。そこまでして分かることは「gated が届かなかったのか、
届いた先が失敗したのか」だが、エッジから見ればどちらも「このルートが 502 を返している」で
あり、alert として鳴らしたい条件は同じである。区別が要る場面が出るまでは足さない。

## Consequences

入口を通った1リクエストごとに 1 行が出る。ログの量はトラフィックに比例する。切る手段は
用意したが、既定で有効であることに意味がある——切っている状態は「記録しないと決めた」
状態であり、忘れた結果ではない。

証明書の期限と更新の失敗が alert にできるようになる。ADR 0014 が「更新に失敗しても既存の
証明書は残す」と決めているため、失敗は静かに積み上がる。その静かさを補うのがこの gauge で
ある。

fail-open の穴（ADR 0002）が alert にできるようになる。`NetworkRole` が対象を解決できて
いない状態は、いままで見に行った人しか気づけなかった。

ログに書かないと決めたものは、後から追えない。ログインの失敗をクエリ文字列から追う、
といった調査はできない。必要になれば、その経路のハンドラが自分の言葉で（トークンの値では
なく、何が起きたかを）書くほうが安全である。

メトリクスのラベルを Ingress に寄せたため、「どのホストが遅いか」は Ingress 単位でしか
分からない。1つの Ingress が複数のホストを持つ構成では粒度が足りない。足すならホスト名
ラベルだが、そのときは時系列の数を見積もってから決める。
