# 0012. 担当する Ingress の決め方とルーティングの優先順位

- Date: 2026-08-21
- Updated: 2026-08-22（正規形でないパスを 400 で拒否することにした。「書き換えない」は維持している）
- Status: Accepted

## Context

ADR 0001 はルーティングの入力を標準の `networking.k8s.io/v1` Ingress に決め、独自のルーティング CRD を作らないとした。Ingress の語彙は限られており、パスの照合は `Exact` / `Prefix` / `ImplementationSpecific` の3つしかない。

その語彙が何を意味するかは、Kubernetes の仕様が完全には決めていない。`ImplementationSpecific` はその名のとおり実装が決めるものであり、複数の Ingress が同じホストとパスを主張したときにどちらが勝つかも、どの Ingress を自分の担当と見なすかも、仕様の外にある。

決めないままにすると、これらは「informer がたまたま返した順」に決まる。同じ manifest がレプリカごとに別の宛先へ流れ、再起動のたびに変わる。ルーティングの誤りはログに出ず、間違ったアプリケーションが応答するという形でしか現れない。

## Decision

### `ImplementationSpecific` は `Prefix` として扱う

移行対象の manifest には `pathType` を持たないものが含まれ、API サーバはそれを `ImplementationSpecific` として保存している。広く使われている Ingress Controller はこれを前方一致として解釈しており、既存の manifest はその挙動を前提に書かれている。`Exact` として扱うと、移行した瞬間にサブパスがすべて 404 になる。

### `Prefix` はパスセグメントの境界で照合する

`/foo` は `/foo` と `/foo/bar` に一致し、`/foobar` には一致しない。文字列としての前方一致にすると、あるアプリケーションのために書かれた規則が、名前がたまたま似ているだけの別のアプリケーションのトラフィックを飲み込む。宣言した側からは見えない形で起きるため、境界を無視しない。

宣言側の末尾のスラッシュは無視する。`/a/` と `/a` を別の規則として扱う理由が無い。

### ホストの段はフォールスルーする

ホストは完全一致、`*.example.com` 形式のワイルドカード、ホスト未指定の順に見る。上位の段がそのホストを知っていても、そのパスを主張していなければ探索は終わらず、次の段が答える。

「ホストが一致した時点でそのホストの規則だけを見る」という解釈も取り得るが、その場合、あるホストに1つでも限定的な規則を足した瞬間に、それまでワイルドカードが受けていた残り全部が 404 になる。規則を足す操作が、足していない経路を壊す方向に働くのは避ける。

### 競合は作成時刻で決める

同じホストとパスを2つの Ingress が主張した場合、古いほうが経路を保つ。作成時刻が同じ場合は namespace と名前の順で決める。

これは競合を許すという意味ではなく、競合が起きたときの結果を予測可能にするという意味である。順序に依存させると、どのレプリカに届いたか、直前に何が再起動したかで宛先が変わる。既に動いているものが勝つほうが、あとから足した誤った宣言によって既存の経路が奪われるより安全である。

### `defaultBackend` は全ホストの最後の受け皿

どの段のどのパスにも一致しなかったとき、はじめて `defaultBackend` を見る。複数の Ingress が持っている場合は上と同じ順序で最初のものを使う。

### 担当かどうかは `--ingress-class` で決める

`spec.ingressClassName` を明示している Ingress は、その名前が `--ingress-class` と一致すれば担当する。IngressClass オブジェクトの中身は見ない。フラグが契約であり、IngressClass オブジェクトを作り忘れただけで既存の Ingress が全部止まるのは割に合わない。

`spec.ingressClassName` を持たない Ingress は、既定の IngressClass が `--ingress-class` の名前を持ち、かつその `spec.controller` が gated を指している場合にだけ担当する。名前だけで拾うと、他人が所有する同名の IngressClass が gated にトラフィックを渡せてしまう。

IngressClass の `spec.controller` の値は `gate.unstable.cloud/ingress-controller` とする。

非推奨の `kubernetes.io/ingress.class` アノテーションは見ない。ADR 0008 は移行を `ingressClassName` の変更で行うと決めており、2つ目の経路を用意する理由が無い。

### リクエストのパスは書き換えない。正規形でなければ受け付けない

`/a/../b` のような正規形でないパスを**書き換えない**。書き換えれば「照合したパス」と「バックエンドが受け取るパス」が食い違い、その食い違いこそが取り違えの温床になる。

当初はここで「拒否もしない」と決めていた。これを改め、**正規形でないパスは 400 で返す**ことにする。照合もせず、転送もしない。

改めた理由は、認可の判定（ADR 0017）がパスを文字列の前方一致で見ることにある。`/api*` を許可する規則を書くと、`/api/../admin` がその許可に乗ったうえで、バックエンドには `/api/../admin` のまま届く。バックエンド側のフレームワークはこれを `/admin` として応答するものがほとんどなので、許可していないパスが許可の下で開く。実際に手元で成立することを確かめてある。

拒否は書き換えと違い、食い違いを作らない。照合したパスと転送するパスがずれるのは「通した場合」の話であり、通さないなら両方とも存在しない。標準ライブラリの `ServeMux` も正規形でないパスをハンドラに渡さない前例がある。

拒否するのは次の3つである。

- デコード後のパスに、`.` または `..` だけのセグメントがある
- セグメントの `;` より前が `.` または `..` である。`;` 以降をパラメータとして捨てる実装があり、そこでは `..;` が `..` として働く
- パスのエンコードされた形が `%2F` または `%2E` を含む（大文字小文字を問わない）。スラッシュとドットをエンコードで隠すと、gated が見る形とバックエンドが見る形がずれる

拒否しないものも決めておく。空のセグメント（`//a`、`/a//b`）、`%20` のような通常のパーセントエンコード、`;` を含むセグメント（`/a;jsessionid=x`）、末尾のスラッシュは、すべて通す。空のセグメントは前方一致を越える手段にならず、`//` を黙って畳む実装の前提で書かれたアプリケーションを壊す理由が無い。

検査するのは 443 番だけである。80 番は何もバックエンドへ転送しないので、そこを通り抜けても届く先が無い。

## Consequences

同じ入力からは、どのレプリカでも、何度再起動しても同じテーブルができる。テーブルの構築とマッチングは Kubernetes の型に依存しない純関数なので（ADR 0007）、ここに書いた規則はすべてテーブルテストとして列挙されている。

既存の manifest は `ingressClassName` の変更だけで移行できる（ADR 0008）。`pathType` の書き足しも、アノテーションの追加も要らない。

代償として、競合の解決を作成時刻に委ねたため、「新しく書いた宣言が効かない」という形の失敗が起こりうる。原因は古いほうの Ingress であり、新しいほうを見ても分からない。競合を `status` やイベントに出すことは今回実装しない。

パスを書き換えないことは、認可の判定（ADR 0002）が同じパスをどう扱うかと揃っている必要がある。片方だけが正規化すると、認可を通り抜けたパスと転送されるパスがずれる。拒否はこの条件を満たす唯一の対処であり、認可の側は何も変えずに済む。

代償として、`..` を含む URL を実際に使っているクライアントは 400 を受け取る。そのようなクライアントは、これまでも `..` を畳む前段の実装の下では別のパスに届いていたはずで、意図した宛先に届いていたとは考えにくい。
