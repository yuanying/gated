# 0036. 依存の更新だけの週は、パッチ版を機械が出す

- Date: 2026-10-21
- Status: Accepted

## Context

依存の更新は Renovate が PR として運んでくる（ADR 0027）。届いた PR は CI が全層で判定し（ADR 0026）、人がマージする。マージされた更新が配備に届くのは、さらに人が版タグを打ったときである（ADR 0029）。

この二段の手作業のうち、判断が要るのはどちらでもない場合が多い。パッチ版とダイジェストの更新は、CI が緑なら人がマージを押すだけになっている。マージを押すだけの PR は溜まり、溜まった PR は上流の修正を配備から遠ざける。版タグも同じで、依存の更新しか入っていない週に、人が版を選び、メッセージを書く理由は無い。書くことが「依存を上げた」しか無いからである。

一方で、人が書いた変更を機械がリリースしてはいけない。ADR 0029 が版タグを人の手に置いたのは、「main が緑であるコミットに打つ」という判断と、タグのメッセージに何が変わったかを書く仕事があるからである。機能の変更はそのどちらも要する。

gated は fraction-agents・natsumi などと同じ Renovate の GitHub App で動いており、同じ時期に同じ方式を入れる。

## Decision

### パッチ・ダイジェスト・pin の更新は Renovate がマージする

更新の種類がパッチ版、ダイジェスト、pin（`pin` と `pinDigest`）のものは、PR のチェックがすべて通ったら Renovate 自身がマージする。マイナー版とメジャー版は PR を開くだけで、従来どおり人がマージする。グループの PR は、含まれる更新がすべて自動マージの対象であるときだけ自動でマージされる。kubernetes monorepo のグループにマイナー版が1つでも入れば、そのグループは人が見る。

マージの可否は Renovate がチェックの結果を見て決め、GitHub の auto-merge やブランチ保護には頼らない（`platformAutomerge` を切る）。このリポジトリにはブランチ保護が無く、それを足すかどうかはこの決定の範囲の外にある。チェックを無視する設定は使わない。

ci.yml は PR ごとにパスで絞らずに走るので、Renovate が書き換えうるどのファイルの PR にも、live 層を除く全層の判定が付く。チェックが1つも無いブランチを Renovate は pending として扱いマージしないので、仮に判定の付かない PR が生じても自動ではマージされない。

自動マージの前提として、公開から7日経っていない版は提案させない（`minimumReleaseAge`）。公開直後に取り下げや修正が入った版が、人の目を通らずに main に入ることを避ける。

### 前回の版から Renovate のコミットしか無ければ、週に一度パッチ版を出す

release.yml が週に一度（月曜 09:00 JST）と手動の起動で、main に対してだけ動く。最新の版タグから main の先頭までが次の2つを両方満たすとき、パッチ版を1つ上げた版タグを打つ。

| 条件 | 見るもの | 満たさないとき |
|---|---|---|
| マージ以外のコミットの作者がすべて `renovate[bot]` | 最新の版タグから先頭までのコミット | 人の変更が1つでもあれば何もしない。リリースは人が打つ |
| イメージの中身に関わるファイルが変わっている | 同じ範囲の差分 | ワークフロー、`renovate.json`、テストの足場だけの更新ではリリースしない |

イメージの中身は Dockerfile とそれがコピーするもの（`go.mod`・`go.sum`・`cmd/`・`internal/`）である。これ以外の変更は、どれだけ入っていてもイメージを変えない。

どちらかを満たさなければ、何もせずに成功で終わり、理由をログに残す。人の変更が入った週が続く限り、機械はリリースしない。人がタグを打てば、そこからまた数え直しになる。

最新の版タグは `vX.Y.Z` の形のものだけを、数として比べて選ぶ。版タグが1つも無ければ何もしない。最初の版を選ぶのは人である。

判定は `hack/release-plan` に置き、`make release-plan` で手元からも同じ問いを発せる。判定そのものは git に触れない純関数で、ユニットテストの層（`make test`）で固める（ADR 0007）。ワークフローにしか無い判定を作らないという ADR 0026 の考えに倣う。

### 機械が打つタグも注釈つきにする

人の打つ版タグは注釈つきで、メッセージに何が変わったかを書いている。機械のタグも同じ形にする。1行目は版と「依存の更新」であることを書き、本文に含まれる Renovate のコミットの件名を並べる。

### イメージを先に push し、タグは後から打つ

実行ごとに発行されるトークンで push したタグでは、ほかのワークフローが起動しない。したがって機械がタグを打っても、publish.yml はそのタグのイメージを焼かない。

release.yml は publish.yml を呼び出して、これから打つ版の名前でイメージを push し、それが成功してからタグを打つ。イメージの名前は依然として「そのイメージを作った git ref の名前」であり（ADR 0029）、その ref がこれから付く、という順序になっただけである。イメージの push に失敗すればタグは残らない。タグが指すイメージが存在しない、という状態を作らない。

人が版タグを push したときは、これまでどおり publish.yml がそのタグで起動してイメージを焼く。

### 書き込む権限は書き込むジョブにだけ持たせる

release.yml の先頭は読み取りのみとし、パッケージへの書き込みは publish.yml を呼ぶジョブに、リポジトリへの書き込みはタグを打つジョブにだけ与える。どちらのワークフローも PR では起動しない。publish.yml を判定と同じファイルに置かなかった ADR 0029 の理由は、release.yml にもそのまま当てはまる。

## Consequences

パッチ版とダイジェストの更新は、人の手を経ずに main に入り、依存の更新しか無い週には配備できる版タグになる。配備側が版を上げるのは、配備側の Renovate の仕事である。

ADR 0029 の「版タグの元になる git タグは人が打つ」は、「人の変更を含む版タグは人が打つ」に狭まった。機械が打つのは、CI が全層で判定した Renovate のコミットだけからなる版である。「main が緑であるコミットに打つ」という人の手順は、機械の側では、緑でなければマージされないことで代わりに担保される。ただし main の先頭そのものの CI 結果は見ていない。

ADR 0027 が代償として挙げた「マージするまでは PR が溜まる」は、マイナー版とメジャー版に限られるようになった。

人の変更と Renovate の更新が同じ週に入ると、その週の依存の更新は人のリリースを待つ。この ADR を入れる変更そのものも人のコミットなので、次に人が版タグを打つまで機械はリリースしない。意図した動作である。

Renovate のブランチに人がコミットを足した場合（生成物の再生成など）も、そのコミットは人のものとして数えられ、機械はリリースしない。

Go の tool ディレクティブだけの更新も `go.mod` を変えるので、バイナリが変わらなくてもパッチ版が出ることがある。tool の依存は MVS を通じてバイナリの依存も動かしうるため、区別しない。

自動でマージされた更新が壊れていた場合、CI の層で見えないものはそのまま版になる。live 層は CI に入らないので（ADR 0025）、実在の認証局との相互作用で壊れる更新は、配備されるまで見つからない。
