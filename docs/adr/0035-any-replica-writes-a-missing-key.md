# 0035. 署名鍵の Secret が無ければ、どのレプリカでも作る

- Date: 2026-10-16
- Status: Accepted

## Context

gated は2つの署名鍵を Secret に置き、全レプリカで共有している。セッション Cookie の署名鍵（ADR 0003、ADR 0006）と、バックエンドへ渡すアサーションの署名鍵（ADR 0034）である。どちらも、Secret が無ければ gated が生成して書き、既にあれば上書きしない。どちらも、鍵を読めていないレプリカは ready にならない。

これまで、鍵を生成して書くのはリーダーだけだった。全レプリカが同じ鍵で署名しなければならないので、鍵を決めるのは1つのレプリカに限る、という理由である。

この組み合わせは、版上げで行き詰まる。アサーションの署名鍵を導入した版へ、それより前の版からローリング更新したときに、実際に次のことが起きた。

1. 新しい版の Pod は、アサーションの署名鍵を読めるまで ready にならない。
2. 鍵の Secret はまだ無い。作るのはリーダーの役目である。
3. リーダーの Lease は、古い版の Pod が持ち続けている。古い版は鍵の存在を知らないので作らない。
4. 新しい Pod はリーダーになれず、鍵が無いので ready にならない。ready にならないので、Deployment は古い Pod を消さない。古い Pod が消えないので Lease も手放されない。

誰も鍵を作らないまま、更新が止まる。抜けるには運用者が Secret を手で作るしかなかった。

同じ形は、セッションの署名鍵にもある。セッションの鍵の生成は最初の版からあるので、版上げだけでは起きない。ただし `--session-key-secret` が指す Secret を別の名前に変えて更新すると、古い Pod のリーダーは古い名前の Secret しか知らず、新しい名前の Secret を作らない。新しい Pod はそれを読めないので ready にならない。運用者が Secret を消した場合も、リーダーの生成は起動時に一度走るだけなので、次にリーダーが替わるまで作り直されない。どちらも「鍵を読めない限り ready にならない」レプリカが「自分では作れない」ことから来ており、アサーションの鍵と同じ行き詰まりである。

## Decision

### 鍵の生成をリーダー限定から外し、全レプリカで行う

セッションの署名鍵とアサーションの署名鍵の生成を、どちらも全レプリカの責務にする。各レプリカは起動時に Secret を確かめ、無ければ新しい鍵を生成して作る。既にあれば、中身が使えなくても触らない。

これは ADR 0034 の「Secret が無ければ、リーダーが新しい鍵を生成して書く」を置き換える。セッションの鍵について ADR 0006 が前提にしていた「鍵を決めるのはリーダー」も、同じように置き換える。

### 同じ鍵で署名することは、作成の排他で守る

全レプリカが同じ鍵で署名する、という ADR 0006 と ADR 0034 の要求は変わらない。それをリーダー選出ではなく、API サーバの作成の排他で守る。

- 鍵を書く操作は Secret の作成だけである。更新も上書きもしない。
- 同じ名前の Secret を作れるのは1回だけである。複数のレプリカが同時に作りにいっても、成功するのは1つで、残りは「既にある」として失敗する。
- 「既にある」で失敗したレプリカは、それを誤りとして扱わず、先に作られた鍵を使う。
- 全レプリカは、生成した自分の鍵ではなく、Secret から読んだ鍵で署名する。

したがって、どのレプリカが作っても、全レプリカが読むのは最初に作られた1つの鍵になる。リーダー選出に頼っていたときよりもむしろ確かである。Lease は同時に2つのリーダーが居ないことを保証しない（ADR 0006）が、作成の排他は API サーバが保証する。

### 生成は起動時に一度だけ行う

鍵の生成は、これまでどおり起動時に一度走って終わる。Secret が後から消えたときに見張って作り直すことはしない。消えた鍵が作り直されるのは、次にいずれかのレプリカが起動したときである。それまで、動いているレプリカは最後に読めた鍵を使い続ける。

鍵を作り直すことは、セッションの鍵では全セッションの失効、アサーションの鍵では手順を飛ばした交換になる（ADR 0003、ADR 0034）。運用者が消したことに気づかないまま、動いているプロセスが黙ってそれを起こすことはしない。

## Consequences

アサーションの署名鍵を導入した版への更新が、手作業なしで進む。新しい Pod が自分で Secret を作り、それを読んで ready になる。古い版がリーダーのまま残っても関係しない。`--session-key-secret` や `--assertion-key-secret` の指す先を変える更新も同じように進む。

鍵の生成はリーダー選出の分担表（ADR 0006）で「全レプリカ」の側に移る。リーダーが落ちている間に止まるものから、鍵の生成が外れる。

API サーバへの書き込みが、レプリカの数だけ起動時に1回ずつ増えうる。Secret が既にあれば読み取り1回で終わるので、増えるのは Secret が無いときだけであり、そのとき失敗する作成も高々レプリカの数である。

Secret を作る権限は全レプリカに要るが、全レプリカは同じ ServiceAccount で動いており、その権限は既に持っている。RBAC は変わらない。

アサーションの鍵を導入した版（v0.4.0）は、この決定より前の形で出ている。その版へ古い版から上げる場合は、行き詰まりを避けるために Secret を先に作っておくか、この決定を含む版へ直接上げる。
