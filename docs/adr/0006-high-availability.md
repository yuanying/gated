# 0006. 高可用構成とリーダー選出

- Date: 2026-08-21
- Updated: 2026-08-22（Ingress の `status.loadBalancer` 書き戻しを分担表に足した。ADR 0032）
- Status: Accepted

## Context

現行の ingress-nginx は複数レプリカの Deployment として動いており、LoadBalancer Service 経由でトラフィックを受けている。1つの Pod が落ちても、あるいはノードのメンテナンスで退避しても、サービスは継続する。gated でもこの可用性は維持したい。

しかし ADR 0001 でコントローラとプロキシを単一プロセスに同居させたため、レプリカを増やすと ACME による証明書発行も同時に複数走ることになる。同じドメインに対して複数の Pod が同時にオーダーを出せば、無駄な発行が起き、Let's Encrypt のレート制限をレプリカ数の分だけ速く消費する。チャレンジの応答も、どの Pod がオーダーを出したかによって答えるべきトークンが変わる。

## Decision

全レプリカが同じプロセスを動かし、証明書の発行だけをリーダーに限定する。

| 責務 | 実行するレプリカ |
|---|---|
| Ingress / NetworkRole / NetworkRoleBinding の watch | 全レプリカ |
| HTTP のルーティングとプロキシ | 全レプリカ |
| 認証・認可の判定 | 全レプリカ |
| ACME による証明書の取得・更新 | リーダーのみ |
| Ingress の `status.loadBalancer` 書き戻し | リーダーのみ |

書き戻しをリーダーに限るのは、証明書とは理由が違う。全レプリカが書いても結果は同じであり、壊れるものは無い。ただし同じ内容の更新が API サーバへレプリカの数だけ飛ぶ。読む側が得るものが何も無い書き込みなので、1つに寄せる（ADR 0032）。

リーダーの選出には Kubernetes の Lease を使う。controller-runtime のリーダー選出機構をそのまま利用する。

証明書は Secret に書き込まれる（ADR 0005）ため、リーダーが取得した結果は informer 経由で全レプリカに伝わる。レプリカ間で直接通信する経路は持たない。

### チャレンジ応答の共有

HTTP-01 のチャレンジは、Let's Encrypt がどのレプリカに到達するか分からない。リーダーだけが応答できる状態では検証が確率的に失敗する。

そのため、リーダーがオーダーを開始した際にチャレンジのトークンを Secret に書き込み、全レプリカがそれを読んで応答できるようにする。証明書の取得はリーダーの責務だが、チャレンジへの応答は全レプリカの責務である。

### 共有される状態

レプリカ間で共有する必要があるものはすべて Kubernetes のリソースとして表現し、informer 経由で配る。プロセス間の直接通信は行わない。

| 共有するもの | 置き場所 |
|---|---|
| 証明書と秘密鍵 | Secret（`kubernetes.io/tls`） |
| ACME アカウント鍵 | Secret |
| ACME チャレンジのトークン | Secret |
| セッション Cookie の署名鍵 | Secret |

セッションはステートレス（ADR 0003）であり、署名鍵さえ共有されていればどのレプリカでも検証できる。セッションアフィニティは不要である。

## Consequences

現行と同じ複数レプリカ構成を維持でき、Pod の入れ替えでサービスが途切れない。ローリングアップデートも通常の Deployment として扱える。

リーダーでない Pod も証明書とチャレンジトークンを読むだけで完全に機能するため、リーダーの交代がトラフィック処理に影響しない。リーダーが落ちている短い間は証明書の取得だけが止まるが、既存の証明書は有効なままである。

状態の共有をすべて Kubernetes に委ねたため、レプリカ間の合意形成やゴシップのような機構を持たずに済む。代償として、API サーバが利用できない間は新しい証明書が取得できず、設定の変更も反映されない。ただし既にキャッシュしている内容でルーティングと認可は継続するため、トラフィックは流れ続ける。この「API サーバが落ちてもトラフィックは止まらない」性質は、認可判定を API サーバに問い合わせない設計（ADR 0002）と一貫している。

チャレンジトークンを Secret に置くため、オーダー開始から検証完了までの間に Secret の書き込みと informer への伝播が挟まる。伝播が間に合わないうちに Let's Encrypt が検証しに来ると失敗する。リーダーは Secret を書いたあと、自分以外のレプリカがそれを読める状態になるまで待ってからチャレンジの準備完了を通知しなければならない。

Lease による排他は「同時に2つのリーダーが存在しない」ことを保証しない。ネットワーク分断時には旧リーダーが自分をリーダーだと思ったまま動きうる。この場合に起きるのは証明書の二重発行であり、レート制限の消費以外の実害はない。厳密な排他のためにコストを払うだけの理由はないと判断する。
