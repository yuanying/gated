# 0009. 起動設定の与え方

- Date: 2026-08-21
- Status: Accepted

## Context

gated は ACME のディレクトリ URL、連絡先、中央認証ホスト、Identity Provider のクライアント情報、各種 Secret の置き場所、リーダー選出の namespace といった設定を必要とする。ADR 0005 はこれらを CRD ではなくコントローラの起動設定として与えると決めたが、その具体的な形は決めていない。

これらの値は例外なく環境固有である。どのホストを認証の入口にするか、どの namespace に Secret を置くかは、動かす場所ごとに違う。一方でリッスンするアドレスやリーダー選出のタイムアウトのように、どこで動かしても同じでよい値もある。

設定を取り違えたまま起動できてしまうと、その失敗はプロセスの起動時ではなく、最初のリクエストや最初の証明書取得のときに現れる。gated はクラスターの入口であり、そこで初めて気付くのでは遅い。

## Decision

設定はコマンドラインフラグで与える。設定ファイルの形式は定義しない。項目数が数十で収まり、Deployment の manifest に並べて読めるうちは、フラグのほうが「いま何が設定されているか」が一目で分かる。

### 既定値を持たせる範囲

環境固有の値には既定値を与えず、未指定なら起動を拒否する。ACME のディレクトリ URL と連絡先、中央認証ホスト、Secret の参照、namespace がこれにあたる。

既定値を持たせるのは、どこで動かしても同じでよい値に限る。リッスンアドレスはワイルドカードへのバインドであり場所を選ばない。リーダー選出のタイムアウトも同様である。IngressClass の名前だけは `gated` を既定とする。これは gated 自身の名前であって環境の名前ではない。

「未指定なら何かにフォールバックする」形は採らない。たとえば namespace を「自分が動いている namespace」で補うと、同じ manifest が置かれた場所によって別のものを指すことになり、設定を見ても何を指しているか分からなくなる。

### Secret の参照の形

Secret は `namespace/name`、Secret の中の特定のキーは `namespace/name/key` の形で指定する。namespace は常に明示する。

gated は自分の namespace の外にある Secret（証明書、チャレンジトークン）も読み書きするため、namespace を省略できる形にすると、省略時の意味が参照ごとに変わる。

### 検証の粒度

検証は最初の1件で止めず、見つかった問題をすべて報告する。各問題には対応するフラグ名を添える。設定ミスを1つずつ潰すために再起動を繰り返さずに済ませるためである。

検証は設定の構造体上の純関数として書く。ファイルシステムにも API サーバにも触れないため、規則をすべてテーブルテストで列挙できる（ADR 0007）。「Secret が実在するか」のような外部の状態に依存する確認は、ここではなく実際に読む時点で行う。

### Identity Provider の最低数

GitHub と Google のどちらも設定されていない場合は起動を拒否する。保護対象への未ログインアクセスは中央認証ホストへのリダイレクトで終わる（ADR 0003）が、その先にコネクタが1つも無ければリダイレクトは行き止まりになる。行き止まりであることは起動時に分かるので、そこで止める。

## Consequences

設定漏れがプロセスの起動失敗として現れる。Pod が CrashLoopBackOff になり、ログにフラグ名と理由が並ぶ。トラフィックが流れ始めてから気付く経路が減る。

環境固有の値がリポジトリに残らない。既定値が無いということは、コードにもドキュメントにも実際のホスト名や namespace を書く場所が無いということである。

代償として、最小構成でも渡すフラグが多い。開発時に手元で起動するにも一式を並べる必要がある。フラグの数が manifest で読み切れなくなった時点で、設定ファイルの導入を検討することになる。

Identity Provider を必須にしたため、「認可は使わずルーティングと証明書だけ使う」構成が取れない。gated の目的が3つの統合である以上、その構成を第一級の使い方として支える理由は薄いと判断する。必要になれば、認証機能そのものを無効にするフラグを足す形になる。
