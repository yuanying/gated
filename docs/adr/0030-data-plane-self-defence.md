# 0030. データプレーンの自己防衛

- Date: 2026-08-22
- Status: Accepted

## Context

gated はクラスターの唯一の入口として 80 番と 443 番をインターネットに向けている。相手を選べない場所に立っているのに、持っている期限はリクエストヘッダの受信（20 秒）だけだった。

足りていないものは3つある。

**アイドルな keep-alive 接続を回収しない。** `http.Server.IdleTimeout` を設定していないと `ReadTimeout` に従い、それも未設定なので0になる。接続を張って何も言わない相手を、こちらから閉じる手段が無い。

**遅い送信者と遅い読み手に期限が無い。** ボディを 1 バイトずつ送り続ける相手、応答をまったく読まない相手を切れない。gated は貯めずに流すので、こういう相手1本につきバックエンドへの接続も1本塞がる。塞がる先はこちらではなく、守るべきアプリケーションのほうである。

**バックエンドへの接続を使い回さない。** 標準の既定 Transport は1ホストあたりアイドル接続を2本しか保たない。

一方で、この入口を通る正規の利用には次のものが含まれる。数百 MiB のアップロード。数分にわたって少しずつ届く LLM の応答。何十分も無通信で張られたままの WebSocket。**これらを壊す期限を入れるくらいなら、期限を入れないほうがましである。**

期限の意味には2通りある。「全体で何秒」と「連続する2回の入出力の間で何秒」である。前者を選ぶと、上の3つが全部壊れる。ingress-nginx が `client_body_timeout` / `send_timeout` で採っているのは後者であり、gated が移行元としてきた挙動もそれである。

## Decision

### 期限は「間隔」であって「全体」ではない

クライアントのボディの読み取りと、クライアントへの応答の書き込みに期限を置く。ただし期限が掛かるのは入出力1回であって、リクエスト全体ではない。

- **ボディの読み取り**: 連続する2回の読み取りの間が期限を越えたら切る。全量に期限は無い。1 GiB のアップロードは、途切れずに届いている限り何時間でも通る
- **応答の書き込み**: 書き込み1回が完了するまでに期限を越えたら切る。書き込みと書き込みの間隔には期限が無い。「次のトークンまで5分」の LLM ストリームは、その5分のあいだ書き込みが発生しないので何も起きない。切れるのは、送ったものを読まないクライアントだけである

期限は毎回の読み書きの直前に張り直し、終わったあとに残さない。残すと、長い無通信のあとの最初の書き込みが即座に失敗する。

### Upgrade した接続には掛けない

WebSocket などにアップグレードした接続は、その時点で下の接続を横取りして双方向にコピーする形になり、上のラッパーを通らなくなる。横取りの時点で、それまでに張った期限も消す。

無通信の WebSocket を切ってよいかは、アプリケーションと利用者の都合であって、エッジが決めることではない。切りたければアプリケーションが ping を送る。

### 値

| 項目 | 値 | 意味 |
|---|---|---|
| keep-alive のアイドル | 90 秒 | 次のリクエストが来ないまま空いている接続を閉じるまで |
| リクエストヘッダの受信 | 20 秒 | 変更なし |
| クライアントのボディの読み取り間隔 | 60 秒 | 上記のとおり全量ではない |
| クライアントへの書き込み1回 | 60 秒 | 上記のとおり間隔ではない |
| バックエンドへの接続（dial） | 10 秒 | |
| バックエンドとの TLS 握手 | 10 秒 | 今は平文でしか話さないので出番が無い |
| バックエンドの応答ヘッダ待ち | 無制限 | 下記 |
| バックエンドごとのアイドル接続 | 32 本 | 全体で 256 本、90 秒で回収 |
| 転送のコピーに使うバッファ | 32 KiB を使い回す | |

これらはフラグにしない。どこに配備しても同じでよい値であり、環境ごとに変える理由が見当たらない（ADR 0009）。変える理由が実際に出てきたら、そのときフラグにする。

90 秒は、ingress-nginx の既定（75 秒）とアイドル接続の回収周期を揃えた値である。60 秒は、正規の利用がその間まったく何も送らない／読まないことは無い、という判断による。どちらも「これを越えたら異常」の線であって、性能の調整値ではない。

### バックエンドの応答ヘッダは待ち続ける

バックエンドが最初の1バイトを返すまでの期限は置かない。生成に数分かかる応答が正規の利用として存在する。

固まったバックエンドを抱えたままにならないかという心配は要らない。クライアント側の期限が先に働き、クライアントが去ればその転送は取り消される。バックエンドはクラスターの中にあり、信用している相手である。

### 自分で守らないもの

| 守らないもの | 理由 |
|---|---|
| リクエストボディの上限 | gated は貯めずに流すので、自分のメモリを守る必要が無い。守る相手はバックエンドのディスクだが、大きなボディを受けるアプリケーションはそれを意図して受けている。全体に1つの上限を置くなら最大の要求に合わせるしかなく、それは保護にならない。個別に変えるにはアノテーションを読むことになり、それは ADR 0002 とは別の設計判断になる |
| Ingress ごとの期限の調整 | 上の期限は「間隔」なので、移行元で長い秒数を指定していた経路も、指定しないまま通る。調整する理由がそもそも消えている |
| バックエンド側の読み取り期限 | 上記のとおり |
| 接続数の上限・レート制限・WAF | 誰が通れるかは `NetworkRole` が決めている（ADR 0002）。必要になったらその語彙の中で考えるほうが一貫する |
| 前段のロードバランサを信用する設定 | ADR 0013 のとおり、今は持たない |

## Consequences

正規の利用は何も変わらない。大きなアップロード、長いストリーム、無通信の WebSocket は、いずれもこの期限に触れない。触れるのは、接続を張って黙る相手、ボディを 1 分以上止める相手、応答を 1 分以上読まない相手だけである。

期限は「間隔」なので、**リクエスト全体の長さに上限は無い**。1 バイトずつ 59 秒おきに送り続ける相手は、いつまでも接続を保てる。これは意図した妥協である。全体の上限を置けば、それは同時に正規の長い転送の上限になる。この形の相手を止めたければ、接続数かレート制限が要り、それは上の表のとおり今回は持たない。

期限を毎回の読み書きの直前に張り直すので、読み書きごとに1回、下の接続に期限を設定する費用がかかる。転送するバイト数ではなく読み書きの回数に比例し、1回あたりはシステムコール1つ分に満たない。

アップグレードした接続には何の期限も無い。バックエンドが応答しないまま張られ続ける WebSocket は、どちらかが閉じるまで残る。

期限に掛かった転送は、クライアントから見ると接続が切れるか 502 になる。「遅すぎたので切った」と本文で説明することはできない。応答の途中で切る場合、そこまでに送った分は既にクライアントに届いており、上書きできる状態が残っていないからである。
