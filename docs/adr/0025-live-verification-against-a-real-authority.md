# 0025. 本物の認証局に対する検証は、明示的に呼んだときだけ動く層に置く

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0007 は「本物の外部サービスには接続しない」と決め、その代償として「本物の Let's Encrypt に対する検証は test クラスターでの手動確認に委ねられる」と書いた。委ねた先は、これまで誰も実行していない。

委ねたままにできない理由がある。Pebble と本物の認証局は、同じ RFC 8555 を実装していながら応答が同じではない。実際に、注文の finalize に対する応答へ Pebble は `Location` ヘッダを付けない。ACME クライアント（ADR 0005）はそれに合わせた分岐を持っており、**その分岐の反対側は Pebble に対して一度も実行されない**。自動テストが全部通っても、本物に当てたときに初めて動く経路が残る。

同じことは証明書チェーンの形や、レート制限の応答、`Retry-After` の扱いにも当てはまりうる。Pebble に通ることは、本物に通ることの証明にならない。

一方で ADR 0007 の決定そのものは正しい。自動テストが本物の認証局に繋がれば、テストはネットワークの状態に左右され、レート制限を消費し、DNS の設定を持たない環境では動かなくなる。CI で回せるものではなくなる。

## Decision

ADR 0007 を覆さない。自動テストの層（`go test ./...` / envtest / integration / e2e）は、これまでどおり本物の外部サービスに接続しない。

その上に、**明示的に呼んだときだけ動く `live` 層**を1つ足す。

| 層 | 実行方法 | build tag | 外部接続 |
|---|---|---|---|
| ユニット | `make test` | なし | なし |
| envtest | `make test-envtest` | `envtest` | なし |
| 結合 | `make test-integration` | `integration` | なし |
| E2E | `make test-e2e` | `e2e` | なし |
| live（本 ADR） | `make verify-live` | `live` | 実 ACME と DNS プロバイダの API |

`live` は独立した build tag であり、`go test ./...` にも `make test-e2e` にも入らない。CI が回すのは `live` を付けない層だけである。人が意図して呼んだときにだけ本物に触れる。

### 既定は staging、production は二重に明示させる

ACME ディレクトリの既定は Let's Encrypt の staging とする。それ以外を使うには、ディレクトリの指定に加えて、承知していることを表す別の指定を要求する。本番のレート制限は週単位で回復するため、取り違えの代償が「もう一度実行する」では済まない。

### 環境に属する値は一つもリポジトリに置かない

ゾーン名・ホスト名・IPv6 アドレス・API トークン・連絡先メールアドレスは、すべて環境変数から取る。既定値を持たせない。未設定なら理由を述べて skip する。gated のリポジトリは public であり、運用しているネットワークの情報を置く場所ではない（ADR 0009 と同じ理由）。

skip であって失敗ではないのは、この層が「設備がある人だけが実行できるもの」だからである。設備が無いことは、gated の欠陥ではない。

### 検証用の名前は毎回作って毎回消す

検証には実在する名前と、そこへ到達できる経路が要る。テストが DNS プロバイダの API でレコードを作り、成功・失敗のどちらでも消す。名前は実行ごとに変え、決まった接頭辞を付ける。接頭辞は、消し残しを機械的に見つけるためのものである。異常終了で消し残した場合に備え、次回の実行が開始時に同じ接頭辞のレコードを掃除する。

### E2E のハーネスを作り直さない

live は E2E（ADR 0024）と同じ道具立てで動く。クラスターの生成、イメージの組み立てと読み込み、manifest の適用、後始末——どれも live のために作り直す理由が無い。build tag で切り替わるのは**中身だけ**である。認証局がクラスターの中の Pebble か外の本物か、名前を解決するのがクラスター内の DNS サーバか本物の DNS か、gated へ到達する経路が公開ポートかノードの公開アドレスか、の3点にとどまる。

### 確かめるのは経路であって網羅ではない

live で確かめるのは、本物の認証局に対して注文が最後まで通ることと、**そのときどちらの分岐を通ったか**である。ADR 0024 が E2E について書いたことと同じ理由で、シナリオは増やさない。網羅は純関数のテーブルテストの仕事であり、ここでしか分からないのは「Pebble と本物で応答が違う箇所」だけである。

## Consequences

Pebble にしか当てていない分岐が、実行可能な形で確かめられるようになった。これまで「手動確認に委ねる」と書かれていたものが、コマンド1つになった。

その代わり、この層は実行できる環境を選ぶ。ゾーンを操作できる API トークンと、インターネットから 80 番に到達できるアドレスが要る。持っていない人にとっては常に skip であり、gated の検証にはならない。live を CI に乗せない理由でもある。

本物のレート制限を消費する。staging の上限は緩いが無限ではない。実行ごとに新しい名前を使うため、名前あたりの上限ではなくアカウントあたりの上限に当たる。頻繁に回すものではない。

DNS のレコードを作る以上、消し忘れれば他人のゾーンに残骸が残る。接頭辞と開始時の掃除でそれを検知・回収できるようにしたが、掃除が働くのは次に実行したときである。
