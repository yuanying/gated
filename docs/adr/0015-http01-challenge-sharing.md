# 0015. HTTP-01 チャレンジの共有と応答

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0006 は「HTTP-01 のチャレンジトークンを Secret に書き、全レプリカが応答できるようにする」「リーダーは Secret を書いたあと、他のレプリカがそれを読める状態になるまで待ってからチャレンジの準備完了を通知しなければならない」と決めた。

決まっていないのは、その Secret がどういう形をしているか、応答する側がそれをいつ読むか、そして「読める状態になるまで待つ」を何をもって満たすか、である。

読む側には制約がある。`/.well-known/acme-challenge/` への리クエストはインターネットから誰でも投げられる。1リクエストにつき1回 API サーバを読む実装にすると、そのパスへのリクエストを繰り返すだけで API サーバに負荷をかけられる。

一方でキャッシュを持つと、書いた直後のトークンが読めない時間が生まれる。ADR 0006 が言う「伝播が間に合わないうちに検証しに来ると失敗する」がこれである。

## Decision

### 1つの Secret に JSON でまとめる

チャレンジは namespace ごとに1つの Secret（既定名 `gated-acme-challenges`）の1エントリに、トークンをキーとする JSON オブジェクトとして置く。namespace だけを起動フラグで与え、名前は gated 自身のものとして固定する（ADR 0009）。

トークンごとに Secret のキーを分ける形も取れるが、トークンは推測不能な base64 であってキーとしてまったく読めず、まとめておけば同時更新が素直な read-modify-write になる。

### 照合はトークンだけで行う

応答するかどうかはトークンの一致だけで決め、ホスト名では照合しない。ホストは Secret とログに記録するが、判断には使わない。

トークンは推測不能であり、注文が進行している間しか公開されない。別のホスト名で同じトークンを尋ねられて答えたところで、CA が検証するのは CA が指定したホストであって、攻撃者が選んだホストではない。逆にホストで照合すると、`Host` ヘッダが何らかの理由で識別子と一致しない場合に検証が落ちる経路を作ることになる。得るものより失うもののほうが大きい。

### 読む側はスナップショットを使い回す。ただし空振りは短い間隔で読み直す

応答側はチャレンジの一覧をスナップショットとして保持し、既定30秒は読み直さない。これがインターネットからのリクエストを API サーバへの負荷に変換されないための上限である。

ただしスナップショットに無いトークンを尋ねられた場合だけ、既定1秒の間隔でもう一度読む。書かれたばかりのトークンが「30秒経つまで見つからない」という状態を避けるためであり、空振りが続いても API サーバへの読み取りは毎秒1回を超えない。

読み直しが失敗した場合は直前のスナップショットを使い続ける。API サーバが一瞬いなくなったことを、gated が既に知っているチャレンジの 404 に変えてはならない。

### 「読める状態になるまで待つ」は、書き戻しの確認と待ち時間の2段で満たす

チャレンジを公開する側は、書き込んだあと、それが読み戻せることを確認するまで戻らない。ACME クライアントは戻った瞬間にチャレンジを受理し、CA はその直後に来うる。

その上で、確認できてからさらに一定時間待つ。待つ長さは応答側の「空振り時の間隔」を基準にする。書き込みと同時にスナップショットを取ったレプリカは、その間隔が過ぎるまで読み直さないため、それより短く待つと 404 を返しうる。応答側の30秒ではなく1秒を基準にできるのは、空振りの読み直しがあるからである。

なお ADR 0006 が言う「他のレプリカが読める状態」の厳密な確認（レプリカ数の把握と全レプリカからの確認）は行わない。共有する状態が Kubernetes のオブジェクトである以上、書き戻せることの確認と、応答側のキャッシュの寿命を超える待ちで十分だと判断する。

## Consequences

チャレンジの応答がリーダーかどうかに依存しなくなった。データプレーンは Secret を読むだけで応答でき、リーダーの交代も検証の途中で影響しない。

トークンだけで照合するため、応答側はルーティングテーブルもホスト名の知識も必要としない。80番のハンドラは「gated が待っているトークンか否か」だけを見る。

キャッシュを2段の寿命にしたため、挙動が「常に最新」でも「常にN秒古い」でもなくなった。当たれば最大30秒古い答えを返し、外れれば最大1秒古い答えを返す。前者は、公開を取り下げたトークンにしばらく答え続けることを意味する。注文が終わったトークンに答えても検証は起きないので害は無い。

公開してから受理するまでに固定の待ちが入るため、ホスト数の多い証明書ほど注文に時間がかかる。ホストごとに数秒であり、90日に1度のことなので費用としては小さい。
