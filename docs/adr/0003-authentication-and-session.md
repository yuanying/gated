# 0003. 認証: Identity Provider 連携とセッション

- Date: 2026-08-21
- Status: Accepted

## Context

ADR 0002 で権限の主体を `github:<login名>` / `google:<メールアドレス>` としたため、これらの識別子をブラウザからのリクエストに対して確定させる手段が要る。

自宅クラスターには保護したいホストが複数ある。ログイン状態をホスト間でどう共有するかによって、体験も、Identity Provider 側に登録するコールバック URL の数も変わる。

なお llm-wiki の Web アプリは既に同じ問題を Auth.js で解いており、GitHub と Google を受け入れ、JWT のステートレスセッションを使い、同じ識別子体系を採用している。この設計は実運用で機能しているため、踏襲できるところは踏襲する。

## Decision

### Identity Provider 連携

GitHub と Google を、それぞれ個別のコネクタとして自前で実装する。

汎用の OIDC Relying Party だけを実装する案は採れない。GitHub はユーザーログイン用の OIDC を提供しておらず、OAuth 2.0 で認可コードを交換したのち `/user` API を叩いて login 名を得る必要がある。OIDC の Discovery には乗らない。

Dex を前段に置いて OIDC に一本化する案も検討したが採らなかった。cert-manager への依存を消すことがこのプロジェクトの目的の1つであるのに、代わりに別の常駐コンポーネントを増やすのでは差し引きが合わない。

コネクタは interface として切り、GitHub・Google・汎用 OIDC を並列に実装できる形にする。Identity Provider を増やす際はコネクタを1つ足す。

Google のメールアドレスを識別子に使うため、認可コード交換で得た ID トークンの `email_verified` が真であることを必ず確認する。未検証のアドレスを信用すると、任意のアドレスを自称する第三者に権限を与えてしまう。

### 中央認証ホスト

ログインの入口を1つのホスト（中央認証ホスト）に集約する。保護対象のホストへ未ログインでアクセスした場合、まず中央認証ホストへリダイレクトし、そこで Identity Provider とのやり取りを完結させ、元のホストへ戻る際にそのホスト限定のセッション Cookie を発行する。

親ドメインに Cookie を発行して全サブドメインで共有する案は採らなかった。実装は最も簡単だが、セッション Cookie が同じドメインの全ホストへ送られる。信用しないアプリケーションを同じドメインに置けなくなり、また異なるドメイン（複数のドメインでサービスを公開している）には効かない。

ホストごとに独立してログインさせる案も採らなかった。Identity Provider 側の体感はほぼワンクリックで済むものの、保護対象のホストを増やすたびに GitHub と Google の双方へコールバック URL を登録する運用が発生する。

中央認証ホストに集約すれば、Identity Provider へ登録するコールバック URL は1つで済み、かつ Cookie のスコープはホスト単位に保てる。

### セッションの保持

セッションは**署名付き Cookie** に入れる。サーバ側にセッションの実体を持たない。

Cookie に入れるのは「誰であるか」（識別子と有効期限）だけである。「何にアクセスできるか」は Cookie に入れず、リクエストのたびに `NetworkRole` / `NetworkRoleBinding` を評価して決める。権限を変更したときに、既にログインしている利用者へ即座に反映させるためである。

Cookie は `HttpOnly` / `Secure` / `SameSite=Lax` を付ける。署名鍵は Secret に置き、全レプリカで共有する。

## Consequences

ステートレスであるため、セッションストアも、その冗長化も、ガベージコレクションも要らない。レプリカ間で共有するのは署名鍵だけであり、どのレプリカにリクエストが届いても同じ結果になる。

一方でセッションの即時失効ができない。Cookie を無効化する手段が有効期限切れしかないため、権限を剥奪しても、その人の Cookie が失効するまでは「認証済みの誰か」として振る舞える。ただし権限そのものはリクエストごとに評価されるので、`NetworkRoleBinding` を消せばアクセスは即座に拒否される。実害が出るのは、識別子そのものを信用できなくなった場合（アカウント乗っ取りなど）に限られる。この場合は署名鍵を差し替えて全セッションを一括で無効化する。有効期限は短めに設定して被害の窓を狭める。

中央認証ホストを挟むため、初回アクセス時のリダイレクトが1往復増える。また中央認証ホスト自身が単一障害点になる。ただし同じコントローラのプロセスが応答するため、独立したコンポーネントが増えるわけではない。

GitHub の login 名は改名できる。改名されると権限が外れてアクセスできなくなるが、これは他人に見えてしまう方向ではなく見えなくなる方向の失敗であり、安全側に倒れている。

コネクタを自前で持つため、Identity Provider 側の仕様変更に追従する責任を負う。GitHub の `/user` API のような、OIDC の標準に乗っていない部分は特にそうである。
