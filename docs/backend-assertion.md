# バックエンドでアサーションを確かめる

gated は、主体が決まった要求をバックエンドへ転送するとき、`Gated-Assertion`
ヘッダに署名付きのアサーションを付ける。決定とその理由は
[ADR 0034](adr/0034-conveying-the-subject-to-the-backend.md) にある。この文書は、
それを使う側——アサーションを確かめるバックエンドと、鍵を管理する運用者——の
ための手順をまとめたものである。

例のホスト名は架空のものである。中央認証ホストを `auth.example.com`、守られる
アプリケーションを `shop.example.com` とする。

## 何が届くか

| 要求 | `Gated-Assertion` |
|---|---|
| セッション Cookie でログイン済み | 付く |
| `AccessToken` で認証された | 付く。Cookie の場合と区別できない |
| 未ログインで、`system:unauthenticated` に許された | 付かない |
| 未ログインで、どの `NetworkRole` にも参照されない Ingress へ来た | 付かない |
| ログイン済みで、どの `NetworkRole` にも参照されない Ingress へ来た | 付く |

クライアントが自分で付けた `Gated-` で始まるヘッダは、どの要求からも gated が
削ってから転送する。gated の後ろでは、`Gated-` で始まるヘッダは gated が付けた
ものだけである。アプリケーションが同じ接頭辞のヘッダをクライアントから受け取って
いたなら、それは届かなくなる。

アサーションは要求ごとに新しく署名され、期限は発行から60秒である。WebSocket
などの長い要求でも、確かめるのは要求の始まりの1回なので、期限が要求の長さを
縛ることはない。

## 確かめる手順

バックエンドは、要求のたびに次の順で確かめる。どれか1つでも満たさなければ、
その要求を未認証として扱う。主要な言語の JOSE ライブラリはどれも、2〜7 を
設定として受け付ける。

| 段 | 確かめること | 注意 |
|---|---|---|
| 1 | `Gated-Assertion` ヘッダがある | 無ければ未認証 |
| 2 | JWS の compact 形式で、ヘッダの `alg` が `EdDSA`、`typ` が `gated-assertion+jwt` | 受け付ける `alg` は自分の設定で `EdDSA` だけに固定する。アサーションに書かれた値を信じない |
| 3 | `kid` の公開鍵が、自分の設定に書いた JWKS にある | JWKS の URL はアサーションから読まない。知らない `kid` なら、間隔を空けて一度だけ取り直す |
| 4 | その公開鍵で署名が検証できる | |
| 5 | `iss` が自分の設定に書いた発行元（例 `https://auth.example.com`）と一致する | `--auth-host` にポートを付けていれば、ポートも含む |
| 6 | `aud` が自分の公開ホスト名（例 `shop.example.com`）と一致する | 比べる相手は自分の設定であって、要求の `Host` ヘッダではない |
| 7 | `exp` が過ぎておらず、`iat` が未来すぎない | 時計のずれとして数十秒までを許す |
| 8 | `sub` が、自分が許す主体の一覧にある | `NetworkRoleBinding` と同じ主体をここにも書く。gated の設定が素通しになったときにも、この段が残って断る |

1〜7 は「gated が、このホストについて、この主体を認証した」ことの確認で、8 は
「その主体を自分が許す」ことの判断である。

6 で `Host` ヘッダと比べてはいけないのは、`Host` を送る側が自由に書けるからで
ある。別のホスト宛てのアサーションを `Host` ごと持ち込まれると、`Host` と比べる
実装は通してしまう。

### 設定に持つもの

| 値 | 例 |
|---|---|
| 発行元 | `https://auth.example.com` |
| JWKS の URL | `https://auth.example.com/__gated/jwks.json` |
| 自分の公開ホスト名 | `shop.example.com` |
| 許す主体 | `github:alice` など |

JWKS の応答には `Cache-Control: public, max-age=300` が付く。キャッシュしてよい。
中央認証ホストが落ちていても、キャッシュした鍵で検証は続けられる。

### 閉じ込められるのはホストまで

`aud` はホスト名であり、パスは入らない。同じホストの下にパスで分けた別々の
バックエンドが居れば、一方が受け取ったアサーションを期限内にもう一方へ持ち込む
ことができる。互いを信用しないアプリケーションは、別のホストに置く。

## 鍵の Secret

鍵は `--assertion-key-secret` で指定した Secret（`Opaque`）に置く。

| エントリ | 中身 |
|---|---|
| `signing-key` | 署名に使う Ed25519 の秘密鍵1つ。PKCS #8 の PEM（`PRIVATE KEY`） |
| `published-keys` | 署名には使わず、公開だけする鍵を0個以上。PEM のブロックを並べたもので、各ブロックは秘密鍵（`PRIVATE KEY`）でも公開鍵（`PUBLIC KEY`）でもよい。使うのは公開鍵の側だけである |

JWKS には、`signing-key` の公開鍵を先頭に、`published-keys` の公開鍵を続けて
載せる。同じ鍵が両方にあれば1つにまとめる。

Secret が無ければ、リーダーが `signing-key` だけを持つ Secret を作る。既にある
Secret は、中身が読めなくても書き換えない。その場合はログにエラーを出し、どの
レプリカも ready にならない。一部でも読めないものがあれば、Secret 全体を読めない
ものとして扱う。交換の途中で鍵が1つ黙って落ちるのを避けるためである。動いて
いるレプリカは、最後に読めた鍵を使い続ける。

各レプリカは Secret を5分ごとに読み直す。

## 鍵の交換

gated が時刻を見て鍵を替えることはない。交換は運用者が Secret を書き換えて行う。
新しい鍵は Ed25519 の秘密鍵を PKCS #8 の PEM で用意する（`openssl genpkey
-algorithm ed25519` が出力する形）。

1. 新しい鍵を `published-keys` に足す。全レプリカが読み直し、バックエンドが
   JWKS を取り直すまで待つ。目安は、読み直しの間隔（5分）と JWKS のキャッシュ
   （5分）を足した10分以上である。
2. 新しい鍵を `signing-key` に移し、それまでの `signing-key` を `published-keys`
   に移す。
3. 古い鍵で署名したアサーションの期限（60秒）が切れ、全レプリカが読み直した
   あとで、古い鍵を `published-keys` から消す。

公開を先にするのは、レプリカが Secret を読み直す時期がそろわないからである。
先に公開しておけば、どのレプリカがどちらの鍵で署名していても、バックエンドは
検証できる。

署名鍵が漏れた場合は、手順1を飛ばして2から行い、古い鍵をすぐに消す。その間、
新しい鍵をまだ知らないバックエンドでは一部の要求が落ちる。落ちる方向の失敗で
あって、通ってはいけない要求が通る方向ではない。

Secret を消した場合、作り直されるのは次にリーダーが決まったとき（再起動や
リーダーの交代）である。それまで、動いているレプリカは最後に読めた鍵で署名し
続ける。作り直された鍵への切り替わりは、手順1を飛ばした交換と同じ結果になる。

## 版上げ

ADR 0034 より前の版から上げる場合に必要なのは、起動フラグを1つ足すことだけで
ある。

| 項目 | 内容 |
|---|---|
| 起動フラグ | `--assertion-key-secret=<namespace>/<name>` を Deployment の引数に足す。既定は無い。足さずに上げると、Pod はフラグ名を出して起動を拒否し、CrashLoopBackOff になる |
| Secret | 用意しなくてよい。初回の起動でリーダーが作る。`--session-key-secret` とは別の Secret を指す。同じものを指すと起動を拒否する |
| RBAC | 変わらない。Secret の読み書きの権限は既にある |
| readiness | 署名鍵を読めるまで、レプリカは ready にならない |
| リクエストヘッダ | クライアントが付けた `Gated-` で始まるヘッダは、転送されなくなる |

`config/manager/deployment.yaml` を overlay の元にしているなら、このフラグは既に
そこに書かれている（gated と同じ namespace の `gated-assertion-key`）。自前の
Deployment を持っている場合は、同じ形の1行を足す。

上げた直後から、ログイン済みの要求に `Gated-Assertion` が付く。読まない
バックエンドの挙動は変わらない。
